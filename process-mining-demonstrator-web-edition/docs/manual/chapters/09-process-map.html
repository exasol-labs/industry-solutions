9 The Process Map

The process map is the flowchart canvas at the heart of the application. It appears in almost every view mode — A-Chart, B-Chart, both panels of the A/B Comparison, Individual Journey, the left pane of Happy Path, Conformance Check and the Simulation "Flow" tab — and it always behaves the same way. This chapter explains the canvas in detail: how nodes are drawn and what their badges mean, how start and end markers are placed, how edges encode the selected metric, how grouping boxes collapse and expand, and how you zoom, pan, drag and reset the layout. It then covers the four view modes built directly on the canvas: the A-Chart and the B-Chart, the A/B Comparison with its Process Goodness and Process Similarity tinting, and the Individual Journey. This chapter is for every user; the two role-restricted views built on the same canvas (Conformance Check and Happy Path) have chapters of their own.

Nodes

Every process step in the filtered result set is drawn as one coloured node. Shape and colour come from the step definition held in the database, not from anything you set on the canvas, so the same step always looks the same in every chart and every view mode.

Shape valueAppearance
stadiumPill with fully rounded ends. This is the default when a step defines no shape.
roundRectangle with a 12 px corner radius.
circleCircle.
hexFlat-top hexagon.

Background and foreground colours are also per step. They may be given either as a named SwiftUI colour (a legacy of the desktop edition the web edition was ported from) or as a six-digit hex value. Any value the application cannot resolve falls back to the accent blue, so an unexpectedly blue node usually means a malformed colour in the step definition rather than a rendering fault.

What a node shows

The node always carries the step name. A second line underneath it is filled according to the following order of precedence:

  1. If the step carries an event time — which happens only in Individual Journey mode — the time is shown as HH:MM:SS in 24-hour notation.
  2. Otherwise, if Show node descriptions is enabled and the step has a description that differs from its name, a truncated description is shown: the first 20 characters followed by an ellipsis.
  3. Otherwise the node shows only its name.

Hovering a node shows the full description as a tooltip, or the step name if there is no description. The description line is controlled by the setting processmap.showNodeDescriptions, which is on by default and is reached from the sidebar under Config.

Badges

Up to three badges can be attached to a node. They are independent of each other and can appear together.

End-of-process dot
An orange dot marking a step that is flagged endOfProcess in its definition. This is a property of the step itself — it says "this is a legitimate place for a journey to finish" — and is not derived from the current data.
Score badge
Shows the step's score. The badge is green when the score is greater than zero, red when it is less than zero, and blue when it is exactly zero. Steps without a score carry no badge.
Note badge
A yellow ✎ badge appears when the node has one or more notes attached, with the tooltip "This node has notes". Click the node and choose Show Notes to read them.
Note Node scores drive the Graph Value KPI tile: it is the sum of step score × visits over all scored nodes, where the visit count of a node is the larger of its incoming and outgoing occurrence totals. If no step in the project carries a score, the tile is hidden entirely rather than showing zero.

Start and end markers

The map annotates where journeys enter and leave the process, derived purely from the currently visible transitions:

  • A green downward arrow — a dot, a stem and an arrowhead — is drawn above every node that has no incoming transitions. That node is a process start under the current filters.
  • An orange arrow is drawn below every node with no outgoing transitions. That node is a process end under the current filters.

When grouping boxes are visible the markers are offset so that they clear the box outline rather than overlapping it.

Tip Start and end markers are recomputed from the filtered graph, so they change as you narrow the date window or exclude steps. A node that suddenly grows a green start marker usually means the step that used to precede it has been filtered out.

Selecting a node and its context actions

Clicking a node opens a context popover titled with the step name. The popover is the primary way of drilling into the process from the canvas.

Require and Exclude are mutually exclusive per step: applying one always clears the other, so you cannot accidentally require and exclude the same step at the same time. Both immediately trigger a reload of the chart you are working in.

Warning When the chart's data source is a simulation slot (Sim-A or Sim-B), the source is read-only: Require in journeys and Exclude from journeys are hidden from the popover and only the description and notes items remain. A red notice at the top right of the canvas states this — "Sim-A: simulation data is read-only — interactive filtering, drill-down and step editing are not available."

9.9 Aggregates (developers)

Developers can abstract several connected sub-processes into Σ super-steps on one high-level map. Click Σ Select steps to aggregate (lower-left of the map) to enter pick mode, then click a set of interconnected steps. Choose ＋ Add group to bank that group and start another — banked steps are ringed and locked, so a step can belong to only one aggregate. Bank as many groups as you need.

Choose Create map to open a dialog with one row per group. Each group is checked to be a single interconnected set (a step with no connection to the others is rejected) and takes a Σ step name, a detail-project name, and its own target (same schema, a new schema, or a different connection). It produces (the original project is never modified):

One high-level project
A full copy of the map where each journey's run through each group collapses into that group's single Σ event. The normal engine then computes every Σ node's black-box metrics — its frequency, the time spent inside the group, and the incoming/outgoing edges to the rest of the map — while internal transitions disappear. A Σ step inherits the group's swimlane when its members share one.
One detail project per group
Only that group's events, so each sub-process can be opened on its own and drilled into.

Each Σ node's menu offers two ways to drill down, and both show the same figures — the real numbers the un-aggregated map would show for the current date range, derived live from the source project:

⤵ Drill down · new panel
Opens the aggregate's real steps in a pop-up panel, wired to the steps just before and after it (drawn dashed, for context). The panel shows the date range and journey count, carries the same metric pills as the main map, and is resizable — drag its corner and the chart re-fits. Close it with ✕ or Esc.
⤵ Drill down · in place
Bursts the Σ step open within the current map: its real steps replace the Σ node and connect to the same neighbours, while everything else stays where it is. Several Σ steps can be expanded independently. A detail node's menu (and a button above the map) offers ⤴ Drill up to collapse it back.

Drill-down is read-only and always follows your current date window, refreshing when you move the slider or apply a filter, so a Σ step's detail and the high-level map always tell the same story. To add more aggregates later, open the high-level map, enter pick mode again, select more original steps and choose Add to map — the map is rebuilt from its source with the new Σ step(s) added, and only the new detail project is written.

Dragging nodes

Nodes can be dragged freely. They snap to a 20 px grid, and the new position is written to storage only when you release the pointer, not continuously during the drag.

Layouts are stored server-side per user, and they are keyed by project and by chart mode. A-Chart, B-Chart, Happy Path, Conformance, each simulation slot (sim_<slot>) and each individual journey (ij_<eventId>) therefore keep completely independent arrangements of the same steps. Because the storage is server-side, your layouts follow you to another browser or machine and are included in backups.

Spotlighting a step's connections

Dense maps with many overlapping edges can be hard to read. To isolate one step, hover the pointer over its node and hold still for the dwell time — one second by default. The node and its immediate neighbours brighten and every transition that enters or leaves it stays at full strength, while all other nodes and edges fade to the background. This makes a single step's inputs and outputs easy to trace even in a crowded chart.

The dwell time is the Highlight Trigger setting in Configuration → Steps: choose 1 s (default), 2 s or 3 s, or Off to disable the spotlight entirely. The choice is stored per user, so it follows you between browsers and machines.

The spotlight clears as soon as you move the pointer off the node, or when you click, pan or drag. Nothing is saved — it is a momentary, read-only aid. It is available on every process map except the Individual Journey, whose single trace is already strictly sequential and needs no untangling.

Each edge is one observed transition from one step to another. Five metrics can be displayed, selected with the metric chips in the "Date & Metrics" card above the chart:

Thickness, opacity and colour

Thickness and opacity always encode the selected metric. Line width runs from 3 px to 22 px and alpha from 0.3 to 0.8, scaled linearly against the largest value among the currently visible edges — so the encoding is relative to what is on screen, and changing the filter can make a formerly thin edge thick. The arrowhead scales with the line width.

Colour is a separate channel. When Colorise edges by weight is on, each edge is tinted along the gradient configured for the active metric; when it is off, all edges are grey and only thickness carries the value.

Edge labels

Every edge carries a label with the metric value:

  • Count is shown compactly — for example 1.2k or 3.4M.
  • Time metrics are shown as Ns, Nm, N.nh or N.nd depending on magnitude.
  • A missing time value is shown as —.

The label tooltip reads "<from> → <to> · <occurrences>", which gives you the raw occurrence count even while a time metric is displayed. A yellow ✎ bubble sits next to the label when the transition has notes, with the tooltip "This transition has notes".

A transition from a step to itself is drawn as a self-loop: a circle above the node, without an arrowhead.

Clicking an edge

The edge line has a wide invisible hit area, and the label itself is clickable too, so you do not have to hit the stroke exactly. In the normal charts a click opens a popover titled "<from> → <to>" containing ✎ Show Notes (N). (In Conformance Check's edit mode the same click opens the norm editor instead — see the Conformance Check chapter.)

The colour-scale legend and the Edge Colour Wizard

When graph.edge.colorizeByWeight is on — it is on by default — a small legend card floats over the canvas showing the current metric name, a ⚙ icon and a Low→High gradient bar. If the neutral schema is selected the bar is replaced by the text "No color scale".

The transition table behind the chart

Every edge on the map is one row of the underlying directly-follows graph. To read the exact figures rather than compare edge widths, open the transition table: the raw data the chart is drawn from, shown in full with all metrics at once.

The table is reached from a ▦ Transitions button in the lower-right of the canvas. That button is hidden by default; switch it on under Configuration → Layout → Transition-table button (see §8.5.4). It is offered only on the A-Chart, B-Chart and the two A/B-Comparison panels — not on the Individual Journey, Conformance or Happy Path maps.

The panel lists one row per transition with these columns: From, To (self-loops are marked ↺), # Count, % Outgoing (the transition's share of its source step's departures), Journey % (its share of all filtered journeys), and Avg, Min, Max time and Std Dev — a dash where a time statistic is unavailable. A search box filters by step name, and clicking any column header sorts by it (click again to reverse); the table opens sorted by Count, largest first. A count above the table reports how many transitions match and the total occurrences. The view is read-only and reflects exactly the graph currently drawn, filters and all.

A ⧉ Copy button copies the rows currently shown (in their current filter and sort order) to the clipboard as tab-separated values, ready to paste straight into a spreadsheet. The copied data uses raw numbers rather than the display strings — times in seconds (blank when unavailable) and shares as plain percentages — so it is immediately usable for further analysis.

Grouping boxes

Steps that share a BELONGS_TO value are treated as a group. With Show grouping on (setting processmap.showGrouping, on by default) each group is surrounded by a dashed, tinted box with a coloured name pill. The pill's hue is derived deterministically from the group name, so a given group keeps its colour across charts and sessions.

At the top right of each box sits a round collapse toggle: a red − collapses the group (tooltip "Collapse <group>") and a green + expands it again (tooltip "Expand <group>").

Collapsed groups

A collapsed group is replaced by a single accent-coloured proxy node showing the member count, for example "7 nodes". Edges to and from the members are merged into edges to and from the proxy, and this merging changes the numbers:

  • Connection counts are summed.
  • Times are weighted-averaged.
  • Intra-group transitions are dropped — a transition between two members of the same collapsed group disappears from the map entirely.

A grey hint at the bottom centre of the canvas restates this while any group is collapsed: "Collapsed groups: connection counts summed · times weighted-averaged".

Warning Min Time, Max Time and Std Dev cannot be reconstructed from merged transitions. On an edge that touches a collapsed group these metrics are unavailable and the label shows —. If you need those figures, expand the group first.

Dragging the group box moves all of its member nodes together — or the proxy node when the group is collapsed — which is the quickest way to rearrange a large map.

The A-Chart

The A-Chart is the primary analysis chart and the default view mode. It consists of the KPI strip, the collapsible "Date & Metrics" controls card and the canvas. It is the chart other parts of the application defer to: Statistics always mirrors the A-Chart's filters, AI supported Documentation always analyses the A-Chart dataset, and the Simulation builds its Markov model from the observed A-Chart graph.

When you open a project for the first time, the A-Chart loads immediately using the default window — the last 30 days of data, configurable with graph.defaultWindowDays (0 means the full range). Every other mode is seeded with the same window and the project's real filter bounds but is not loaded until you ask for it.

Flowchart orientation, or Sankey

A small switch floats at the top of the A-Chart and B-Chart canvas with three options — 🕸 Flowchart / ➡ Horizontal / 🌊 Sankey. It flips the same data between renderings; your choice is remembered per user and applies to both charts.

The first two are the same directed-follows flowchart in two orientations. 🕸 Flowchart lays the process out top-down (the default): the start markers are above the first steps and the flow runs downward. ➡ Horizontal lays exactly the same map out left-to-right — layers become columns, the start markers sit to the left of the first steps and the end markers to the right, and the edges curve sideways. Everything else is identical: the node badges, the grouping boxes, the metric on the edges, the node context menu and the transition table all behave the same. Horizontal is often the more natural reading order for a long, mostly-sequential process, or when you want a wide process to fill a wide screen. Node positions you drag are remembered separately per orientation, so switching back and forth never disturbs a layout you have arranged.

The Sankey view draws the process as a left-to-right flow: each band is a transition, and its width follows the currently selected transition metric (the same chips as the flowchart — # Count, % Percentage, Journey %, Avg / Min / Max Time, Std Dev), so switching the metric re-weights the flows just as it re-weights the flowchart's edges. A footer states which metric the widths encode. Nodes are laid out in columns by their distance from the start. Hover any band for its value in that metric plus its share of the source step's outflow and journey count; hover a node for its throughput. Whatever you hover stays lit while everything else dims, which makes a single path easy to trace.

A Sankey has to flow strictly forward, but a process is full of loops. The view resolves this automatically: it finds each cluster of steps that loop among one another — formally, each strongly-connected component of the graph — and collapses it into a single node, marked ↺. The loops that used to tangle the diagram become an "internal loops" count, and the amenities that passengers circulate between (Duty Free ⇄ Dining ⇄ Lounge, for example) become one tidy "airside" node. A collapsed node is named after the members' shared step group when they have one, otherwise after its busiest member. A footer states how many clusters were collapsed. This needs no configuration and works on any process; a purely sequential process simply produces no clusters.

Hovering a collapsed node highlights it and lists every step inside the group, together with the number of internal loops between them — so nothing is hidden by the grouping: you can always see exactly which steps were folded together and why.

The B-Chart

The B-Chart is a second, entirely independent process map. It has the same KPI strip, the same controls card and the same canvas, and it remembers its own filter state (dates, included and excluded steps, meta filters and metric) and its own node layout. Nothing you do on the A-Chart changes the B-Chart or vice versa.

Two things differ from the A-Chart:

  • The B-Chart does not load automatically. Its empty state reads 📊 No Process Data — "Use the sidebar filters and tap Apply to load the B-Chart.", with a Load button.
  • Its loading message is "Loading B-Chart".

Use the B-Chart when you want to keep one configuration of the process on screen while you build a second one — for example one product line against another — and then switch to A/B Comparison to see both at once.

Note Each view mode remembers its own filter state. When you switch modes the application saves the state you are leaving and restores the state of the mode you are entering. Statistics is the exception: it always inherits the A-Chart's filters.

A/B Comparison

A/B Comparison places the two charts side by side — A on the left, B on the right. Each panel has its own header, an optional KPI strip, its own "Date & Metrics" card and its own flowchart. The panels map onto the saved A-Chart and B-Chart states, so anything you already configured in those modes is what you see here. The active side starts as A.

The strip between the two panels carries two buttons. The ⇄ valve synchronises panning, zooming and reset across both sides (see below). Below it, an orientation toggle (➡ when the maps are top-down, ⬇ when they are left-to-right) flips both panels between the top-down and horizontal flowchart layouts at once — the same setting as the A-Chart/B-Chart switch above, so the two stay in step.

Choosing the active side

The sidebar filters can only edit one side at a time. The side currently being edited is the active side, and the panel header tells you which is which: the active panel shows "✎ A-Chart · editing", the inactive one shows "○ B-Chart".

  1. Click the header button of the panel you want to work on. That side becomes active.
  2. Adjust filters in the sidebar, or use that panel's own "Date & Metrics" card, and apply them. Only the active side reloads.
  3. Click the other panel's header to switch, then repeat.

Each panel header also shows that side's journey count ("N journeys") and a chevron that collapses or expands that panel's KPI strip (abpanel.a/b.kpiExpanded, expanded by default). Panel A carries one extra button: ⧉ Copy A's node layout to B, which copies both the viewport and the node positions across so that the two maps line up for visual comparison.

Changing a metric inside one panel's card changes that panel only — and also the shared metric if that panel happens to be the active side.

The valve

Between the two panels sits a ⇄ valve button that controls whether the panels move together.

Data sources per side

Each side's data source is chosen in the sidebar Sampling section and can be the original data, one of the sample sets (Sample 1–3), or a simulation slot (Sim-A or Sim-B). The Active Sample KPI tile on each side names the source it is actually reading — "Original", "Sample 1" … "Sample 3", or "Sim-A"/"Sim-B" — and its value is that source's journey count.

Warning A side fed from a simulation slot is read-only: it shows the red canvas notice and its nodes offer no Require or Exclude actions. You can still read the map, open descriptions and work with notes.

Reading the comparison: Goodness and Similarity

Two figures make the comparison quantitative.

Process Goodness ◔
A server-computed goodness score for one side, shown signed with two decimals. In A/B mode the tile is tinted by comparison with the other side: green when this side is better, red when it is worse, and blue when the two are equal within 0.005. The tile is hidden when the score is null.
Process Similarity ⇄
How alike the two sides are, on a scale of 0 to 1 with two decimals, computed from both sides' journey-path variants together with their graphs. It is tinted green at 0.70 and above, red at 0.30 and below, and blue in between. The tile only exists once a similarity has been computed.

The same similarity figure is repeated as a badge along the bottom row of the comparison — "⇄ Similarity N.NN" — once both sides have been computed, using the identical green/red/blue thresholds.

Empty and loading panels

An unloaded panel shows 📈 with the title A-Chart or B-Chart. The message depends on whether that side is active: the active side reads "Apply filters in the sidebar to load."; the inactive side reads "Tap the header to make this side active, then load." Both offer a Load button, which makes that side active and loads it in one step. While loading, the panel shows a spinner with "Loading A-Chart" or "Loading B-Chart".

Individual Journey

Individual Journey draws exactly one case. Instead of an aggregated map you see that journey's steps in the order they occurred, with the clock time of each event on the node.

Finding a journey

Requires: any user
  1. Switch to Individual Journey from the ☰ "Switch view" menu in the toolbar.
  2. In the sidebar, type into the Event ID field. After two or more characters the field offers autocomplete suggestions.
  3. Pick a suggestion or finish typing the identifier.
  4. Tap Load Journey.

The sidebar's Metrics selector is hidden in this mode, because a single traversal makes counts meaningless: the edge metric is forced to Avg Time.

Reading the journey

On the canvas:

  • Each node shows the event time as HH:MM:SS beneath the step name, in place of the usual description line.
  • Node positions are stored per event ID (chart mode key ij_<eventId>), so rearranging one journey does not disturb another.

The KPI strip is replaced by a journey-specific set of tiles:

TileIconMeaning
Date📅The journey's start date, in short format.
Duration⏱️End minus start of the journey.
Sum of ScoresƒSum of the step scores across the visited steps, shown signed; "—" when no step carries a score.
Steps visited / distinct⑂"total / distinct", where the total is the number of transitions traversed plus one.

The meta tiles are what let you recognise the case in business terms — customer, order number, region, or whatever the project's meta fields have been configured to hold.

Flowchart or swimlane

A small switch floats over the canvas, top-centre, toggling between two layouts of the same journey. It is the only place this choice lives — it is on the canvas, not in the left panel — and it applies only to Individual Journey (the aggregated views, where loops carry meaning, always use the flowchart).

  • 🕸 Flowchart (default) — the directed-follows graph described above. Because it aggregates the case into unique nodes, a revisited step is drawn as a loop back to the same node.
  • 🏊 Swimlane — the journey re-formatted as a strictly sequential layout: one column per event, left to right in time order. A revisited step simply appears again in a later column, so the view has no loops at all — the loop is "unrolled" into repeated, sequential nodes.

In the swimlane, each horizontal lane is a node group (a step's belongs-to group), tinted with that group's colour, and a step sits in its group's lane — so a diagonal edge is the visual signal that the process moved from one group to another. A header row above the top lane carries each event's date and time, and every edge is labelled with the time taken from that node to the next (the elapsed time between the two consecutive events). The swimlane pans and zooms like the flowchart and fits itself to the window when opened; a matching zoom cluster sits in the lower-right corner (zoom out / in with the live percentage, ⤢ fit-to-view, and ↺ reset to 100 %).

Below the lanes the swimlane draws a cumulative-value line chart: for each event it plots the running sum of the step scores from the process start (a YTD-style total), so you can read how the journey's value develops left→right. Each step contributes its own score (positive or negative — the marker is green when it added value and red when it subtracted), the line joins the running totals, and the value at each point is labelled. A dashed zero line appears whenever the running total crosses zero. The chart shares the lanes' horizontal scale — each point sits directly under its step's column — and pans and zooms together with them.

Note The swimlane deliberately has no per-node menu — it is a read-only, at-a-glance timeline of one case. Its columns are evenly spaced by occurrence order, not by real elapsed time; the actual gaps are the edge labels, and the absolute clock times are the header row. The cumulative chart uses each step's score (set in the Step Editor) as its per-step value — the same score that drives journey totals — so steps left at score 0 leave the line flat.

What persists, and where

Because the process map is highly configurable, it is worth knowing what survives a reload and what does not.

Node positionsServer-side per user, keyed per project and chart mode (A-Chart, B-Chart, HappyPath, Conformance, sim_<slot>, ij_<eventId>).
Collapsed-group statePer project and chart mode; restored only when graph.startMode is persisted.
Edge colour schemasPer metric, under graph.edge.colorSchema.<metric>; included in backups.
Selected metricPer chart, as part of that chart's saved state.
KPI strip expansionprocessmap.kpiExpanded, and per panel in A/B (abpanel.a/b.kpiExpanded).
Valve stateabComparison.valveOpen, default open.
Controls-card expansionPer surface: achart.controlsExpanded, bchart.controlsExpanded, abpanel.a/b.controlsExpanded.

Server-side storage means these settings travel with your account rather than with the browser, and they round-trip through the administrator's backups.
