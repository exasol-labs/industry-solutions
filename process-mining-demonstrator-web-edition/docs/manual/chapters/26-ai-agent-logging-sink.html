26 The API Server - Event Receiver

Every other way of getting data into the demonstrator pulls it: you import a file, or the watchdog reads one as it grows. The API Server - Event Receiver is the opposite — it is a small HTTP/HTTPS endpoint the demonstrator opens so that an external program, typically an AI agent, can push journey events into a project as they happen. Each sink is bound to one connection and one project, is protected by its own bearer token, auto-creates any step it has never seen, and can be watched live on a node-based monitor. This chapter explains when to reach for a sink, how an administrator turns the module on, how a developer defines a sink and reads its token, the exact JSON the endpoint accepts, the limits and error codes it enforces, the downloadable agent instructions, and the live monitor.

Requires: Administrator to enable the module; Developer (or Administrator) to define a sink and see its token, in the integration console (HTTP :8100, HTTPS :8463). The running endpoints need no human role — they authenticate the calling program with a per-sink bearer token. The module is off until an administrator enables it.

26.1 What a sink is, and when to use one

A sink is a long-running API server that accepts journey rows over HTTP and writes them straight into a connection's JOURNEYS table, exactly as an import would — the same MD5 pseudonymisation of the case id, the same automatic creation of missing PROJECTS and STEPS rows, the same ORIGINAL sample set. What differs is the trigger and the shape of the data: instead of a file parsed in one run, a sink takes many small JSON POSTs over time, each carrying one event or a short batch of events, from a program you do not control from inside the demonstrator.

Reach for a sink when the source of truth is a live process rather than a log file — most obviously an AI agent that emits a step every time it takes an action, but equally any application that can make an authenticated HTTPS request. Use a file source and the watchdog (chapters 19 and 20) instead when the data already lands in a file, or when you want the parsing, compound-step rules and delta-checkpointing that the extractor gives you. A sink does no parsing: the caller sends already-structured rows.

File import / watchdogAPI Server - Event Receiver
DirectionThe demonstrator pulls from a file.The caller pushes over HTTP.
Shape of dataRaw log lines, parsed by a source type.Structured JSON rows; no parsing.
DestinationAny project id, chosen per run.One fixed project per sink (its project code).
Who may writeA signed-in developer, or the headless watchdog with stored credentials.Any program holding the sink's bearer token.
Unknown stepsCreated automatically.Created automatically.

26.2 Enabling the module

The sink module is opt-in, like Actions. In the admin interface open the Event Receiver tab and tick Enable the API Server - Event Receiver. Toggling the switch takes effect immediately and needs no restart: the sink ports stay bound either way, but while the module is off every request is answered with 503 and nothing is written. The tab also shows how many sinks are configured and whether the sink supervisor process is running.

Each sink listens on a fixed, pre-exposed port from a pool, so the container can publish them once. The pool is HTTP 8120–8129 and, under TLS, the paired HTTPS ports 8483–8492. In the shipped Docker setup these are published on the host with a +10000 offset — HTTP 18120–18129 and HTTPS 18483–18492 — so a caller outside the container uses the host port. The scheme and port that are actually live follow the deployment's TLS mode and certificate, exactly like the other surfaces (see chapter 2): with a certificate in Optional or Required mode a sink answers on its HTTPS port; otherwise on plain HTTP.

Note The module runs as its own supervisor process, one listener per sink. Adding, editing or removing a sink, or a change to the TLS mode or certificate, makes the supervisor rebind its listeners automatically — no terminal, no restart. Enabling or disabling the module does not even need a rebind.

26.3 Defining a sink

A sink is a data source of a new kind, created in the integration console's Sources section like any other.

  1. In the console sidebar open Sources and press ＋ to add a source. For Source type choose API Server - Event Receiver.
  2. Give the sink a name (how it appears in the console and the monitor).
  3. Choose the Connection it writes into. The dropdown lists only the connections assigned to you; the connection must have a schema. This is where the events land, using the connection's stored credentials.
  4. Enter a project code of 1–10 characters (the project's TITLE_SHORT). All of this sink's events go into the one project with that code; it is created on the first write if it does not exist, and reused if it does.
  5. Pick a port from the free ports in the pool. Each option shows both its ports — e.g. HTTP 8120 · HTTPS 8483 — so you can see what an agent will address. Ports already taken by other sinks are not offered; a sink cannot share a port.
  6. Set the TLS preference: ticked (the default) means agents are told to use the sink's HTTPS port, unticked means plain HTTP. This is a per-sink preference for the endpoint shown in the request and the SKILL.md; the listeners still bind whatever the deployment TLS mode allows, and the shown scheme falls back to what the deployment can actually serve, so it never advertises a port that isn't bound.
  7. Save. The confirmation screen shows the sink's bearer token once (see 26.4) and a link to the exact request an agent should send (see 26.6).

One connection can back several sinks (each with a different project code and port), and different developers can each own sinks; you see and manage only your own. A sink whose connection is later unassigned from you, whose port falls outside the pool, or that has no project code, is quietly skipped by the supervisor rather than started.

26.4 The bearer token

Each sink has one secret bearer token that the caller must send on every request. Only a SHA-256 hash of the token is ever stored; the plaintext is shown once, on the confirmation screen right after you create the sink, and cannot be retrieved afterwards. Copy it then and store it wherever the agent keeps its secrets.

If a token is lost or leaked, open the sink in the Sources list and use the 🔑 regenerate action. Because regenerating invalidates the live token the instant it runs — locking out every agent still using the old one — it asks for confirmation first. A fresh token is then minted and shown once; the previous token stops working as soon as the supervisor rebinds (which the console triggers for you). There is deliberately no way to read an existing token back — regeneration is the only recovery.

Handle the token like a password Anyone who holds it can write events into the sink's project for as long as the module is enabled. Send it only over the HTTPS endpoint in any real deployment, never commit it to a repository, and regenerate it if in doubt.

26.5 The ingest API

A sink exposes two endpoints on its port:

POST /ingest
Bearer-authenticated. The body is a single JSON object, or an array of them, each describing one journey event. The events are written to the sink's connection and project; any step seen for the first time is added to STEPS with a freshly allocated activity id, a deterministic colour and shape. Returns {ingested, newSteps, projectId}.
GET /health
Unauthenticated liveness. Returns {"ok": true, "enabled": <bool>} and nothing else — deliberately no sink name or configuration, since anyone who can reach the port sees it.

Authenticate by sending the token as a bearer credential: Authorization: Bearer <token>. Each entry recognises the following fields; only eventId and step are required.

FieldMeaning
eventId (required)The journey / request id — reuse it across every event of one run. It is MD5-pseudonymised on write, so the raw value never reaches the database. Also accepted as event_id.
step (required)A KIND:qualifier naming the request or action (see below) — the whole string becomes one node on the map. An unknown step is created on the fly.
descriptionThe step's detail (the query run, URL fetched, recipient …), up to 256 characters; longer text is truncated. Stored as the event's Action attribute (META_1). Also accepted as meta1.
clientThe calling client — Claude, ChatGPT, …. Stored as the Client attribute (META_2). Also accepted as meta2.
userThe end user, if known. Stored as the User attribute (META_3). Also accepted as meta3.
eventTimeISO-8601 timestamp (a trailing Z is accepted). Missing or blank means “now” on the server. Also accepted as event_time.

The sink writes a per-project METAS row titling the three attribute columns Action, Client and User, so the app labels them in its Metas table and case-level filters — you can filter a project's journeys by client or user.

26.5.1 Naming steps: KIND:qualifier

Keep the step KIND from a small, stable vocabulary and add the specific target after a colon, so each node is self-describing. The first event of a journey names the originating request; each later event names one action taken:

  • SKILL:<skill name> — e.g. SKILL:summarize-sales
  • TOOL:<type>:<tool name> — e.g. TOOL:mcp:airfield_get
  • DATABASE:<database name> — e.g. DATABASE:sales_db
  • WEB:<external|internal>, EMAIL:<external|internal>, FILE:<local|remote>
  • APP:<app name> — e.g. APP:Slack
  • REQUEST — the first event, when the request is not itself a skill or tool call

All the events in one sink land in the one project the sink is coded for; you do not send a project id, and you cannot write into another project through the same sink.

26.6 Example request, and the SKILL.md for agents

A minimal call, against a TLS deployment where the sink's HTTPS port is published on the host as 18483:

curl -sk https://YOUR-HOST:18483/ingest \
  -H "Authorization: Bearer YOUR-SINK-TOKEN" \
  -H "Content-Type: application/json" \
  -d '[
    {"eventId":"req-42","step":"SKILL:summarize-sales","description":"Summarize the Q3 sales report","client":"Claude","user":"alice","eventTime":"2026-09-14T10:00:00Z"},
    {"eventId":"req-42","step":"DATABASE:sales_db","description":"SELECT region, SUM(amount) FROM sales WHERE quarter='Q3'","client":"Claude","user":"alice","eventTime":"2026-09-14T10:00:03Z"},
    {"eventId":"req-42","step":"EMAIL:external","description":"Send the compiled report to alice@example.com","client":"Claude","user":"alice","eventTime":"2026-09-14T10:00:09Z"}
  ]'

You do not have to work the URL out by hand. The confirmation screen (and the 🔌 details action on a sink in the Sources list) opens the ingest-details popup: the exact endpoint URL and a tabbed “Send data to the endpoint” panel of ready-to-run examples, one per language, with the sink's URL and token already filled in. Every tab carries a shared Copy and ⬇ Download button that acts on the tab you are viewing and names the file for that language.

Two fields in that popup make the download ready to use as-is:

  • The endpoint URL is editable and saved per sink. The console auto-detects the host URL, but if agents reach the sink through a reverse proxy or a public domain, type that URL and press Save — it is then shown here and baked into every example on every tab.
  • A token field is pre-filled the moment you create or regenerate the sink; otherwise paste the token you saved. Whatever is in the field is embedded into every example. The token itself is never stored (only its hash is kept), so re-opening the popup in a later session needs a paste — the app says so.

26.6.1 Ready-to-run code in your language

The panel offers the same call in nine forms, sorted alphabetically along the tabs: AI Agents (SKILL.md), C#, CLI (curl), Go, JavaScript, Mojo, Python, Rust and TypeScript. Pick a tab, then Copy or Download it — the downloaded file is named for the language (send_events.py, send_events.sh, SendEvents.cs, send_events.rs, send_events.go, send_events.mjs, send_events.ts, send_events.mojo) or SKILL.md for the agent tab. Each example already contains the endpoint URL and the bearer token from the fields above, the two headers, and the same journey body; when the endpoint is HTTPS (the certificate is self-signed by default) each also disables certificate verification the way that language expects — curl -k, Python verify=False, C#’s ServerCertificateCustomValidationCallback, Rust’s danger_accept_invalid_certs, Go’s InsecureSkipVerify — so it runs against a fresh deployment without edits.

The Python tab, for example, uses requests:

import requests

URL = "https://YOUR-HOST:18483/ingest"
TOKEN = "YOUR-SINK-TOKEN"

events = [
    {"eventId": "req-42", "step": "SKILL:summarize-sales",
     "description": "Summarize the Q3 sales report and email it to the requester",
     "client": "Claude", "user": "alice", "eventTime": "2026-09-13T10:00:00"},
    # … one object per action, all sharing the eventId …
]

resp = requests.post(
    URL,
    headers={"Authorization": f"Bearer {TOKEN}",
             "Content-Type": "application/json"},
    json=events,
    verify=False,  # self-signed cert — point at your CA bundle in production
)
resp.raise_for_status()
print(resp.json())

The other tabs are equally complete: Go uses net/http, Rust uses reqwest + tokio, C# is a .NET 6+ top-level program using HttpClient, JavaScript and TypeScript use Node 18+’s built-in fetch (the TypeScript tab adds an interface for the event shape), and Mojo — which has no native HTTP client yet — drives Python’s requests through Mojo ↔ Python interop.

26.6.2 An example SKILL.md

The downloaded file is plain Markdown with a YAML frontmatter header (so an agent runtime can register it as a skill) and the sink's real URL and token filled in. Abbreviated, it reads:

---
name: AI-Agent-Logger
description: A Skill for logging AI actions into the Process Mining Demonstrator
---

# Skill: Emit process-mining journey events to "Agent Sink"

## How to model a journey
Give every event of one run the same `eventId`. Each event's `step` is a
KIND, qualified after a colon so the map is specific:
- `SKILL:<name>`, `TOOL:<type>:<name>`, `DATABASE:<db>`,
  `WEB:<external|internal>`, `EMAIL:…`, `FILE:…`, `APP:<name>`, `REQUEST`
Put the detail in `description` (≤256 chars → the "Action" attribute);
`client` (Claude/ChatGPT/…) and `user` record who ran it.

## Endpoint
- POST https://YOUR-HOST:18483/ingest
- Authorization: Bearer <YOUR-SINK-TOKEN>
- Content-Type: application/json
- Target project: AGENTLOG

## Request body  (one object, or an array of them)
| field | required | notes |
|-------|----------|-------|
| eventId | yes | the journey id; reuse across a run |
| step | yes | KIND:qualifier — becomes a node |
| description | rec. | the step's detail, ≤256 chars → META_1 (Action) |
| client | rec. | the calling client → META_2 (Client) |
| user | opt. | the end user → META_3 (User) |
| eventTime | no | ISO-8601; defaults to now |

## Example
curl -sk https://YOUR-HOST:18483/ingest \
  -H "Authorization: Bearer <YOUR-SINK-TOKEN>" \
  -H "Content-Type: application/json" \
  -d '[{"eventId":"req-42","step":"SKILL:summarize-sales",
        "description":"Summarize the Q3 sales report",
        "client":"Claude","user":"alice","eventTime":"2026-09-14T10:00:00Z"},
       {"eventId":"req-42","step":"DATABASE:sales_db",
        "description":"SELECT region, SUM(amount) FROM sales WHERE quarter=Q3",
        "client":"Claude","user":"alice","eventTime":"2026-09-14T10:00:03Z"},
       {"eventId":"req-42","step":"EMAIL:external",
        "description":"Send the compiled report to alice@example.com",
        "client":"Claude","user":"alice","eventTime":"2026-09-14T10:00:09Z"}]'

## Responses
200 {ingested, newSteps, projectId} · 400 bad payload · 401 bad token
· 413 too large · 503 module off · 502 destination DB unavailable

Hand that file to the agent and it can log a whole run — a request followed by each action it takes — with no further setup on your side.

Tip Send a short batch (an array) rather than one request per event when your agent produces events in bursts. Each event still becomes one journey row; batching just cuts the number of round trips and transactions.

26.7 Limits and error codes

A sink is the one surface that takes untrusted input from the network, so it is deliberately strict.

StatusWhen
200Written. The body reports how many events were ingested and which step names were newly created.
400The body is not JSON, or an entry is missing a non-empty eventId or step, or an eventTime is not valid ISO-8601. Deterministic — do not retry unchanged.
401Missing or wrong bearer token.
413The request body exceeds the size ceiling (2 MB by default), or carries more than the maximum entries per request (5000 by default). Both are refused before any parsing or database work. Split the payload and resend.
503The module is disabled in the admin interface.
502The destination database was temporarily unavailable. The message is intentionally generic — the underlying driver detail (which names internal hosts, the database user and the schema) is written to the server log, never returned to the caller. Safe to retry after a short pause.

A sink reuses one database connection across posts and refreshes it if it has sat idle, reconnecting and retrying once if a write meets a dropped socket — so a transient network drop surfaces as a brief 502 at worst, not a permanent failure. The two limits are environment-tunable (PMW_SINK_MAX_BODY_BYTES, PMW_SINK_MAX_ENTRIES) for operators who need larger batches.

26.8 The live monitor

The integration console's main pane carries a node-based monitor for sinks, beneath the file-ingestion pipeline and shown once you have defined at least one sink. It is the sink-side sibling of that pipeline: one horizontal lane per sink, reading left to right

[🤖 AI agents] → [🔌 sink : port] → [📊 project] → [🛡 connection]

and refreshed every few seconds. Each lane shows, at a glance:

  • a liveness dot on the sink node — green when the listener answered its health check, red when it did not respond, grey when the module is switched off;
  • the sink's live scheme and port;
  • the event and journey counts for its project, read from the destination database, and when the last event landed;
  • the destination connection and schema.

When a sink's event count grows between two refreshes, its lane lights up with a travelling dot — the “data is arriving” signal, since sinks keep no throughput counter of their own. A sink whose connection cannot be read shows a short problem note on its lane rather than failing the whole view. Because the counts come from the database rather than from the sink process, the monitor reflects everything in the project, however it was written, and the per-connection reads are cached for a few seconds so several open consoles cannot pressure the database.

Note The monitor reads only what the backend can see without contacting the sink processes: stored configuration, whether the module is on and the supervisor alive, a localhost health probe per listener, and the destination-database counts. It does not show per-request throughput or an error history — watch the 502 rate in the server log for that.
