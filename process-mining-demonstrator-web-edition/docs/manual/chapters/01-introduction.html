1 Introduction

This chapter explains what process mining is, what the Process Mining Demonstrator — Web Edition does and, just as importantly, what it deliberately does not do. It introduces the vocabulary used throughout the manual, describes the four audiences the product serves — plain user, power user, developer and administrator — and sets out reading paths so that you can go straight to the chapters that concern you. Read it before any other chapter; every later chapter assumes the terms defined here.

1.1 What process mining is

Business processes leave traces. Every order, claim, application or ticket that passes through a system writes rows into a database: who or what the case was, which activity happened, and when. Process mining takes that raw record — the event log — and reconstructs the process as it actually ran, rather than as it was drawn on a whiteboard.

The starting point is always the same three pieces of information per row: a case identifier that says which end-to-end instance the row belongs to, an activity name that says what happened, and a timestamp that says when. In this application those three columns are EVENT_ID, STEP and EVENT_TIME in the JOURNEYS table. Everything else — colours, scores, case attributes, groupings — is enrichment layered on top.

From that log, four kinds of insight can be derived, and this product provides all four:

Discovery
Sorting every case's rows by time and joining each consecutive pair produces a transition. Aggregating all transitions across all cases produces a directly-follows graph: a map in which each node is an activity and each arrow is an observed hand-over between two activities. This is the A-Chart. Nobody draws it; it is derived entirely from the data, so it shows the rework loops, shortcuts and dead ends that a designed model omits.
Variants
Two cases that visit exactly the same activities in exactly the same order follow the same variant (also called a route or path pattern). Real processes typically have a small number of very common variants and a long tail of rare ones. The Statistics view lists the distinct variants with their frequencies, which is how you separate "the way it usually goes" from "the exceptions".
Bottlenecks
Because every transition carries the elapsed time between its two steps, the map can be weighted by duration instead of frequency. Switching the transition metric to Avg Time, Max Time or Std Dev makes slow and unpredictable hand-overs visible as thick, strongly coloured arrows, and the Statistics view adds a duration histogram, step traffic and a transition heat map.
Conformance
Discovery tells you what happens; conformance tells you whether that is what should happen. You define the intent — a Happy Path (the ideal step sequence, including legitimate alternative branches) or per-edge norms (target values for a metric) — and the application scores the real data against it, edge by edge, and reports the gaps.

Process mining matters because it replaces opinion with evidence. Where an interview produces "approvals usually take a day or two", an event log produces a distribution, a worst case and the exact share of cases that looped back through a rework step. That is the value this product is built to demonstrate.

1.2 What this product is

The Process Mining Demonstrator — Web Edition is a multi-user web application that connects to an Exasol database, reads an event log from it, and visualises how real cases flow through the recorded process. It is the web port of a macOS application of the same name; backup files remain interchangeable between the two.

Concretely, it offers:

  • Ten chart views, selected from the ☰ menu in the top-right of the main area: A-Chart, B-Chart, A/B Comparison, Individual Journey, AI supported Documentation, Statistics, Conformance Check, Happy Path, Notes and Simulation.
  • Journey-level filtering — date window, included and excluded steps, step count, journey time, journey score and three case-level meta attributes — with named, reusable filter presets stored per project.
  • Two independent process maps side by side, with a Process Similarity score between them, so two segments or two time periods can be compared directly.
  • A composite Process Goodness quality score, per-journey inspection with animated replay, annotation of nodes and edges with threaded notes, journey sampling, Markov-model simulation, and a Markdown report generated by an OpenAI-compatible language model.
  • A dedicated administration interface for users, roles, TLS, directory sign-in, logging, backups and licensing, plus a separate integration console for defining data sources and importing event data from files.

1.2.1 Scope: a demonstrator, not a production tool

Warning This application is intended for demonstration and educational purposes only. It is not a production-ready process mining solution. Do not use its output as the sole basis for operational or commercial decisions.

That statement is not a formality; it follows from deliberate design choices which you will meet throughout this manual, and which you should know about before you rely on a number:

AreaDeliberate limitation
Database supportExasol only. There is no adapter for any other database.
Heavy queriesStatistics and Process Goodness run under a 30-second wall-clock timeout; when it expires, the affected tile shows — rather than a partial result.
Process SimilarityAlignment cost is an edge-coverage approximation, not a formal Petri-net alignment, and the variant set is capped at 500 per side (1 000 combined). Past the cap the badge is hidden rather than showing a biased score.
Process GoodnessA relative indicator, not an absolute benchmark. Its constants (alpha 0.5, time penalty 0.01, gamma 0.5) are fixed and not adjustable.
SimulationA first-order Markov model. History-dependent routing, case attributes, resource contention and queueing are not modelled.
Data importEvents are appended and never de-duplicated. Importing the same file twice stores its events twice; to genuinely reload a project you delete the project and import again.
AI documentationLanguage models can produce incorrect, incomplete or misleading results. Every finding must be verified independently.

Used as intended — to show what process mining is, to teach the concepts, and to explore a dataset on an Exasol instance — the product is complete and self-contained, including three generated demo datasets so you can produce a meaningful process map without having any event log of your own.

1.2.3 Two different licences

The manual refers to a "licence" in two unrelated senses; do not confuse them.

Software licence
The source code is distributed under the MIT licence. This governs your rights to the code itself.
Runtime licence
The compute backend requires a signed license.json, uploaded by an administrator under App Control → License. Without one, the application runs in Demo Mode for a one-time grace period (30 minutes by default), after which the backend stops itself until a licence is applied. The admin interface keeps running even then, so a licence can always be uploaded. The grace period is granted once per installation and restarting does not renew it.

1.3 Vocabulary

These terms are used with precise meanings throughout the manual and in the application's own screens.

Journey (case)
One end-to-end instance of a process, identified by EVENT_ID. All rows sharing an EVENT_ID form one journey. "Case" and "journey" are interchangeable.
Step (event)
A single activity within a journey — one row in the JOURNEYS table. On the process map, one node per distinct step name.
Transition
A chronologically consecutive pair of steps within the same journey. On the map, one arrow.
Project
A named body of event data inside one schema, identified by PROJECT_ID. You select a project after connecting; all filters, layouts, presets, norms and happy paths are stored per project.
Connection
A stored bundle of one Exasol server (host, port, credentials, schema, TLS options) and one optional OpenAI-compatible language-model server. Connections are created by administrators or power users and assigned to individual users. You never type a database password into the main application.
Meta attributes
Up to three free-text, case-level columns (META_1–META_3) carrying attributes such as department, region or customer segment. Their business names come from the METAS table.
Variant (route)
A distinct sequence of steps. All journeys following the same sequence belong to the same variant.
Metric
The value that drives an arrow's thickness, opacity, colour and label: Count (the default), Avg Time, Median Time, Min Time, Max Time or Std Dev. Each chart view remembers its own metric selection.
Sample set
A named representative subset of a project's journeys, written to a SAMPLE_SET column on JOURNEYS. Sample sets live in the database and are therefore shared by everyone using that connection.
Norm
A target value attached to one transition for one metric, used by the Conformance Check view. Stored per project and per metric.
Happy Path
A user-defined ideal step sequence, optionally containing named splits with alternative branches, against which real journeys are scored.
Tip The same explanations are available inside the application at any time. Press ⌘/ (or Ctrl+/) to open or close the Help panel; it floats above the application, can be dragged by its title bar and resized from its bottom-right corner.

1.4 Who this manual is for

Four audiences use this product, and every chapter is written with one or more of them in mind. Where a task requires a particular permission, the chapter states it in a callout like this one:

Requires: Administrator

1.4.1 The four audiences

Plain user (Regular user)
The default level for every new account. A plain user explores the process: opens an assigned connection, selects a project, reads the maps and charts, applies filters and saved presets, reads and writes notes, inspects individual journeys, generates AI documentation, and adjusts personal settings such as KPI tiles, node layout, font sizes and theme. A plain user cannot create database connections and does not see the advanced-analysis views.
Power user
A plain user with additional in-application privileges, granted with Make power in the admin Users tab. Power users create, edit, delete and assign their own database connections from inside the main application, provision schemas, generate demo datasets, create and delete journey samples, and use the three advanced-analysis views — Conformance Check, Happy Path and Simulation. They manage only the connections they created.
Developer
An additional grant (the Developer checkbox in the admin Users tab), independent of the level above it. It admits the account to the Integration console, where data sources and their parsing rules are defined and event data is imported into a connection's schema. A Regular user who holds only the Developer grant may enter the console but gains no other elevated powers in the main application.
Administrator
Full control. Everything a power user can do, over every connection rather than only their own, plus exclusive access to the admin interface: all users and roles, TLS certificates and mode, directory (LDAP) sign-in, licensing, logging, backups, login-page customisation, and restarting the servers.

The three permission levels build on each other: Power includes Regular, and Administrator includes Power. The Developer grant is orthogonal and can be combined with any level.

1.6 Reading paths

You do not need to read this manual from cover to cover. Pick the path that matches your role.

1.6.1 Business analyst or plain user

  1. Read this introduction, in particular the vocabulary in section 1.3 — the rest of the manual assumes the terms journey, step, transition, variant and metric.
  2. Read the getting-started chapter: how to sign in, how to open a connection assigned to you, and how to select a project.
  3. Read the chart-views chapter, then the filters and filter-presets chapters. These three cover the everyday loop: load a project, narrow it, press Apply, read the map.
  4. Read the process-map chapter for navigation, node context actions and step groups, and the KPI-panel chapter for the tiles above the map.
  5. Read Process Goodness and Process Similarity when you start comparing segments or periods; both chapters include worked numeric examples.
  6. Read the notes chapter before you begin recording findings, and the configuration chapter when you want to change the default date window, KPI tiles, fonts or step colours.
  7. Skip the installation, admin-interface and integration chapters entirely — nothing in them is required for analysis work.
Tip If you have no data of your own and no power user to help, ask an administrator to generate one of the three demo datasets — Online Bookstore, Online Credit Application, or Flight Booking & Management. Every example in the analysis chapters works against them.

1.6.2 Power user

  1. Follow the business-analyst path first; everything there applies to you unchanged.
  2. Read the connections chapter's power-user sections: creating your own connections with the ＋ button, editing them with ✎, assigning them to other users, provisioning a schema, and generating demo content.
  3. Read the database-setup chapter so you know which database privileges each feature needs — SELECT for reading, CREATE TABLE for notes, ALTER TABLE and INSERT on JOURNEYS for sampling, UPDATE on STEPS for the step editor.
  4. Read Journey Sampling before creating a sample: samples are written into the database and therefore change what every other user of that connection sees.
  5. Read Conformance Check and Happy Path together — both express intent and are scored against the same filtered population.
  6. Read Simulation last, including its limitations section.

1.6.3 Administrator or operator

  1. Read this introduction's section 1.2.2 (the four processes) and 1.2.3 (the two licences).
  2. Read the installation and operations chapter end to end, then perform the first-run checklist: start the stack, sign in to the admin interface, change the seeded administrator password.
  3. Read the database-connections chapter and define at least one connection, test it, and assign it to users.
  4. Read the users chapter: roles, the login gate, failed-sign-in lockout, passkeys and two-factor authentication. Decide these policies before inviting users, because some of them (mandatory two-factor in particular) change what happens at the next sign-in.
  5. Read the TLS chapter and move off plain HTTP. Passkeys require a secure context and a real hostname, so this decision constrains later ones.
  6. Read the backup chapter and enable scheduled encrypted backups; then read the operations chapter's note on backing up the whole data/ directory, which is the only way to preserve the encryption key.
  7. Read the licensing sections and upload the runtime licence before the demo grace period expires.
  8. Keep the logging chapter to hand — it is the first place to look when an import, a rebuild or a connection misbehaves.

1.6.4 Developer or data engineer

  1. Read the vocabulary in section 1.3 and the database-setup chapter, so you know the exact shape of the rows you are producing.
  2. Read the integration-console chapter: the abstraction layer, source types and sources, and how to reach the console.
  3. Read the source-types chapter carefully, including compound steps, helper fields and the ordering rule that the first matching rule wins.
  4. Read the import sections on delta upload, the checkpoint, the transaction bracket and the watchdog before you run an import against real data — in particular the rule that events are appended and never de-duplicated.
  5. Read the pipeline-monitoring chapter for the live flowchart and the ingestion KPIs, especially Events skipped.
  6. If you also automate rebuilds of pre-materialized transitions, read the per-connection API-token section in the administration group.

1.7 Conventions used in this manual

On-screen labels
Controls are named exactly as they appear, in bold — for example Apply, Save Preset…, Use pre-materialized transitions. Icon-only controls are given by their glyph and function, for example the ＋ button in the Connections header.
Code and identifiers
Table names, column names, file paths, environment variables, commands and API endpoints are set in a monospaced face, for example JOURNEYS, PMW_DATA_DIR, data/backups/.
Role callouts
A "Requires" box before a procedure names the minimum permission needed. If you do not hold it, the control described is either hidden or the request is refused.
Note, Tip and Warning
Note adds context you need for the surrounding text to make sense. Tip is optional but saves time. Warning marks behaviour that can lose data, lock someone out, or produce misleading results.
Ports and URLs
Given as the direct-installation defaults (8080, 8090, 8100). Under Docker, add 2000 to each host port. Where TLS is enabled, substitute the HTTPS port (8443, 8453, 8463).
Spelling
The manual uses British spelling; the application's own labels are reproduced verbatim and therefore sometimes use American spelling, as in Colorise edges by weight and Customize.
