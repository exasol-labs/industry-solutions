14 Administration: Database Connections and Directory

This chapter covers the two administration tabs that decide where the application reads its data from and who is allowed to sign in from outside: Database Connections and Directory (LDAP). It explains every field of the connection editor, the TLS options for the database link, how to attach an OpenAI-compatible LLM server and what the built-in SSRF guard will and will not allow, how to list and delete projects, how the optional pre-materialized transitions table works and how to keep it fresh from a scheduler, and how to configure directory sign-in so that directory accounts merge cleanly with local ones. It is written for the person who administers the installation; ordinary users never see these screens.

Requires: Administrator — both tabs live in the admin interface (HTTP :8090, HTTPS :8453) and are reachable only by accounts with the administrator role.

14.1 The Database Connections tab

A connection is a named definition of one Exasol database — host, port, credentials, schema, TLS settings — together with an optional LLM server and a list of the users who may use it. The tab header states the model in one sentence: “Define a database (and optional LLM) server, then assign it to the users who may use it. Each user sees only the connections assigned to them in the main application.”

Two facts follow from that model and are worth internalising before you edit anything:

  • Connections are defined centrally and assigned individually. A user who is not assigned a connection cannot select it, and a direct attempt is refused with “This connection is not available to you.”
  • Every signed-in user gets their own database session against the connection. Users never share a live session, so one user's query can never see another user's transaction. Anonymous mode (sign-in disabled) shares a single session bucket.

14.1.2 The connection editor

The editor has three inner tabs — Database, LLM and Projects — and a common footer with Save (primary), Test connection, Cancel, and, for an already-saved connection, Delete (danger).

The Projects tab button is disabled while the connection is unsaved; its tooltip reads “Save the connection first to list its projects.” After a successful save the editor reloads with fresh data and the Projects tab unlocks. Saving without a name is refused with the toast “Name is required.” Deleting asks Delete connection "<name>"? and is recorded in the log at WARN severity, together with the connection's rebuild token and materialization status, which are deleted with it.

Warning Saving any change to a connection, changing its assignments, or deleting it immediately drops every live session currently using it. Affected users must reconnect. This is deliberate: a revoked assignment has to take effect at once rather than at the end of someone's working day. If a user's connect happens to be in flight while you save, they receive “This connection changed during sign-in. Please reconnect.”

14.2.2 Certificate modes

Verify (system trust store)
The default. The server certificate must chain to a trust anchor the operating system already trusts, and the host name must match.
Pin fingerprint
The driver pins the server certificate to the SHA-256 fingerprint you enter. Colons are stripped, and the remaining value must be pure hexadecimal, 16 to 128 characters long.
Accept any (insecure)
Disables certificate verification and host name checking. Use it only for laboratory or self-signed setups; anyone on the network path can impersonate the database.

Mode parsing is whitespace-tolerant and fails closed: any stored value the application does not recognise — a typo, a legacy record, restored data from an older backup — is treated as Verify, never as “no verification”.

Warning In Pin fingerprint mode a blank or non-hexadecimal fingerprint refuses the connection outright with: “This connection is set to pin a certificate fingerprint, but the fingerprint is missing or not hexadecimal. Enter the server's SHA-256 fingerprint, or change the certificate mode.” This closes an earlier fail-open behaviour in which an unusable fingerprint silently disabled verification while the interface still claimed the certificate was pinned.

14.2.3 Create schema and tables

The banner on the Database sub-tab reads: “Creates the schema named above and the process-mining tables (PROJECTS, JOURNEYS, STEPS, METAS, NOTES) if they don't exist, using the credentials entered here. This requires a database account permitted to CREATE SCHEMA and CREATE TABLE — only your database administrator can grant those rights; this application cannot.”

  1. Enter Host, Port, Username, Password and, crucially, a Schema name. Without one the button reports “Enter a schema name first.”
  2. Optionally tick Also build pre-materialized transitions after provisioning (default off). This is available only in the admin interface.
  3. Click Create schema & tables. The button shows “Creating…” while it works.
  4. Read the result. Success is green: “Created: schema <name>, PROJECTS, JOURNEYS, STEPS, METAS, NOTES”, optionally followed by “· transitions built (N pairs)” or “· transitions build failed: <error>”. Failure is red and shows the database error, or “Could not create the schema.”

Provisioning connects without opening a schema (the target may not exist yet), then issues CREATE SCHEMA IF NOT EXISTS, OPEN SCHEMA and the table DDL in the order PROJECTS, JOURNEYS, STEPS, METAS, NOTES. All DDL uses IF NOT EXISTS, so re-running it never disturbs existing data. If a step fails, the result still lists everything that was created before the failure, so partial progress is visible. The schema identifier is safely double-quoted (embedded quotes are doubled), which means mixed-case and special names work — but remember that a quoted name is case-sensitive in Exasol.

Warning Provisioning uses the password as typed in the form, not the stored one. On a saved connection with a blank password field it runs with an empty password and usually reports an authentication failure even though the saved connection works perfectly. Retype the password before provisioning, testing or generating demo content.
Note Because IF NOT EXISTS leaves pre-existing tables untouched, a JOURNEYS table that already exists does not receive the physical layout the application's DDL declares for new tables. Ask your DBA to apply it manually: 
ALTER TABLE JOURNEYS DISTRIBUTE BY EVENT_ID;
ALTER TABLE JOURNEYS PARTITION BY EVENT_TIME;
Distributing by EVENT_ID co-locates all events of one journey on one cluster node, so the transition query's window function and every GROUP BY EVENT_ID run node-local; partitioning by EVENT_TIME lets Exasol prune by date range.

14.2.4 Assign to users

The right-hand column of the Database sub-tab is headed Assign to users and contains a checkbox for every user account known to the installation. Its empty state is “No users to assign.” Only ticked users see the connection in the main application.

  1. Open the connection and tick the users who need it.
  2. Click Save.
  3. Tell the affected users to reconnect — the save has already dropped any live sessions on this connection.

As an administrator you can see and edit those connections here too — including options such as pre-materialized transitions that the in-app editor does not expose.

14.3.1 The reachability probe

Whenever a user connects, and whenever you press Test connection, the application issues GET <Server URL>/models with Authorization: Bearer <API key> if a key is set, using a 5-second timeout. The server counts as reachable unless the request errors or answers with HTTP 500 or above — a 4xx still means a server is there. With no URL configured the LLM is simply reported as not reachable, which is not an error. Failures are recorded in the log under operation llm-test; the message users see is “LLM server not reachable.”

14.3.2 The SSRF guard

The LLM URL is user-supplied, so the backend validates it before making any outbound request:

  • Only http:// and https:// are accepted — anything else is refused with “Only http:// and https:// URLs are allowed.” A URL without a host gives “The URL has no host.”
  • The host name is resolved and every resolved address is checked. If any one of them is disallowed the whole URL is refused: “The URL resolves to <reason> (<address>); refused.” A host that cannot be resolved gives “The host could not be resolved: <host>”.
  • Always blocked: link-local and cloud-metadata addresses (including 169.254.169.254), multicast, reserved and unspecified addresses. IPv4-mapped IPv6 addresses are unwrapped before the check.
  • Loopback and private (RFC 1918) targets are allowed by default, because a local LLM server — Ollama, LM Studio, an internal vLLM — is a first-class use case. Hardened deployments set the environment variable PMW_BLOCK_PRIVATE_LLM_HOSTS=1 to refuse those too, with the reasons “a loopback address” and “a private address”.
  • The outbound connection is pinned to the vetted IP address, so DNS rebinding cannot swap the target between the check and the connection, while SNI and certificate verification stay bound to the real host name (internationalised host names are canonicalised first so the pin always applies). Redirects are disabled, so a 3xx response cannot bounce the request to an unvetted host.
Note A guard refusal is never shown to end users as an error — the LLM simply appears unreachable. The reason is written to the log as “LLM server URL refused (SSRF guard): …” under operation llm-test. If an LLM you believe to be correct stays stubbornly unreachable, look there first.

14.5.1 Deleting a project

Requires: Administrator (in the main application: ownership of the connection plus the admin, power or developer role).
  1. Open the connection, switch to Projects and press ↻ Refresh so you are looking at current counts.
  2. Click Delete on the project's row.
  3. Read the confirmation carefully: Delete project "<id>"? — “This clears its rows from PROJECTS, JOURNEYS, STEPS, METAS, NOTES and TRANSITIONS_RAW in this schema. This cannot be undone.”
  4. Confirm. The toast reports the scale of what was removed: “Project deleted (N events)”. Failures surface the database error as a toast.

The deletion issues DELETE … WHERE PROJECT_ID = '<id>' against each table in this order — children before the parent:

OrderTableWhat is lost
1JOURNEYSThe event log itself, including every sample set (no SAMPLE_SET filter is applied).
2STEPSStep descriptions, colours, shapes, scores, end-of-process flags and step groups.
3METASThe three meta-column titles.
4NOTESEvery note and comment thread attached to the project.
5TRANSITIONS_RAWThe pre-materialized transition pairs, if the table exists.
6PROJECTSThe project row itself.

Tables that are absent are skipped, not treated as errors — NOTES is created lazily and TRANSITIONS_RAW is optional, so neither is guaranteed to exist. The response lists the tables that were actually cleared. Every deletion is logged at WARN severity under operation connection, naming the user, the project id, the connection and the outcome.

Warning There is no undo and no recycle bin. The application's own backups deliberately exclude event data — they capture settings, presets, layouts and connection definitions, not JOURNEYS — so a deleted project can be restored only from your database's own backups. The project's notes are destroyed with it.

14.6 Pre-materialized transitions

14.6.1 What TRANSITIONS_RAW is and why it exists

The process map is a directly-follows graph. Normally the application computes it live on every reload: a LEAD() window over JOURNEYS pairs each event with its successor (ordered by EVENT_TIME, then STEP_ID), and the result is aggregated into count, average, minimum, maximum and standard deviation of the gap per (from-step, to-step) pair. On large logs that window function dominates the query time, and it is paid again for every filter change.

TRANSITIONS_RAW stores the pairing once: one row per consecutive step pair, with the columns PROJECT_ID, EVENT_ID, FROM_STEP, TO_STEP, FROM_TIME, TO_TIME, DUR_SECS (the gap, precomputed in seconds) and SAMPLE_SET. When the map reads from it, the request-time query is a plain GROUP BY aggregate with no window function at all — in the words of the admin interface, “much faster for interactive filtering on large logs”.

The table is a sixth, optional table alongside the five canonical ones. It is built with CREATE OR REPLACE TABLE … AS SELECT into a staging table so that every column type — critically EVENT_ID, whose type varies between deployments — is inherited from JOURNEYS exactly; a hard-coded type would make the semi-join fail with Exasol's “Incomparable Types” error. The pairing covers every project and every sample set in one pass, partitioning by (PROJECT_ID, SAMPLE_SET, EVENT_ID) because an EVENT_ID is only unique within one project and sample set. After the build the application applies DISTRIBUTE BY EVENT_ID on a best-effort basis (a failure there never aborts the rebuild — distribution is only an optimisation), counts the rows, then drops the old table and renames the staging table into place. Readers are never blocked; the swap leaves a sub-millisecond window with no live table, during which reads simply fall back to the live query.

14.6.2 The per-connection toggle

The banner on the Database sub-tab carries the bold checkbox Use pre-materialized transitions and this explanation: “Reads the process map from a prebuilt TRANSITIONS_RAW table instead of running the windowed query live — much faster for interactive filtering on large logs. It falls back to the live query until the table is built, so rebuild it after each load of JOURNEYS.”

The flag is stored per connection and defaults to off. It is captured when a user connects and re-read on every request, so toggling it takes effect on the user's next reload — they do not have to reconnect. The checkbox exists only in the admin interface; the in-app connection editor used by power users does not expose it, even for connections they own.

With the flag on, the map query reads TRANSITIONS_RAW using the same filter clauses as the live query (the table carries PROJECT_ID, SAMPLE_SET and EVENT_ID). Any read failure — table missing, never built, dropped by a DBA — is non-fatal: the application falls back to the live query so the map never breaks, and logs a warning under operation materialize: “Pre-materialized transitions are enabled but reading TRANSITIONS_RAW failed for project … — falling back to the live query. Cause: …”.

14.6.3 How the application indicates live versus pre-materialized

Users can always see which path served their map. A pill in the detail pane header (not shown in the Individual Journey view) reports the mode:

PillMeaningTooltip
⚡ Pre-materializedThe map was read from TRANSITIONS_RAW.“Transitions are read from the pre-materialized TRANSITIONS_RAW table.”
⚠ Live (not built)The flag is on but the table is unusable, so the live query ran instead.“Pre-materialized transitions are enabled for this connection, but TRANSITIONS_RAW is not built yet — running the live query meanwhile. Rebuild it in the admin interface (Connections → Rebuild now).”
↻ Live queryThe flag is off; this is the normal live computation.“Transitions are computed live from the event log on each load.”

The graph API reports the same information as transitionsMode (materialized, live or fallback) together with queryMs, the server-side wall-clock time of the database queries, which the chart footer displays as, for example, “123 ms” or “1.23 s”. Comparing that figure before and after a rebuild is the simplest way to judge whether materialisation is worth it on your data.

Warning TRANSITIONS_RAW is a snapshot. It goes stale the moment JOURNEYS changes, and nothing rebuilds it automatically — not an ETL load, not demo-content generation, not creating or deleting a sample set. If the table still exists it will serve stale pairs without complaint; if it was never built the map shows “⚠ Live (not built)”. Make a rebuild the last step of every load.

14.6.4 Rebuild now

  1. Open the connection in the admin interface and make sure a Schema is set — a rebuild without one fails with “A schema name is required.”
  2. Save the connection if you have not already; Rebuild now is disabled until then, with the tooltip “Save the connection first”.
  3. Click Rebuild now. The status shows “Rebuilding… (this runs the pairing once and may take a while)”.
  4. Wait for the result: “Built N pairs.” in green, or the error text in red.

The last outcome is stored per connection and shown again whenever the editor is reopened, as one of:

  • “Not built yet — the live query is used until you rebuild.”
  • “Last built: <date> · N pairs.”
  • “Last rebuild failed: <error>” (red).

A rebuild is idempotent and safe to repeat. Two rebuilds of the same connection never overlap — they would race on the staging swap — so a second concurrent call is refused with HTTP 409 “A rebuild is already running for this connection.” Different connections rebuild independently.

Tip When you provision a new schema, tick Also build pre-materialized transitions after provisioning. The table is empty until JOURNEYS is loaded, but its structure exists immediately, so the flag can be switched on straight away and the first real rebuild has nothing to create.

14.6.5 Rebuild from a script (API) and the bearer token

Inside the same banner is a collapsible section headed Rebuild from a script (API): “Let a scheduler (cron / ETL) rebuild this connection right after loading its JOURNEYS, without an admin login. The token below is scoped to this connection only, and calls are rate-limited.”

The endpoint lives on the admin service, not the application:

POST /api/connections/<connection-id>/rebuild-transitions

It accepts either a signed-in admin session or the header Authorization: Bearer <token>, and it uses the connection's stored credentials — so the calling script never handles a database password.

  1. Save the connection. Until then the status line reads “save the connection first”.
  2. Expand Rebuild from a script (API) and click Generate / rotate token. Confirm the dialog: “Generate a new token for this connection? Any existing token stops working.”
  3. Copy the token from the panel headed “New token (copy it now — it is not shown again):” and store it in your scheduler's secret store.
  4. Use the 📋 button to copy the ready-made curl example, which contains the real token while it is still visible on screen: 
    curl -k -X POST \
  -H "Authorization: Bearer <token>" \
  "https://<admin-host>:8453/api/connections/<connection-id>/rebuild-transitions"
  5. Add that call as the final step of the ETL job that loads JOURNEYS.

To rotate, repeat step 2: the new token replaces the old one instantly, so update the scheduler in the same maintenance window. To withdraw access entirely, use Revoke (shown only while a token is set), which confirms with “Revoke this connection's token? A scheduler using it will stop working.” The status line tracks the state as “a token is set for this connection” or “no token set”. Deleting the connection deletes its token as well.

14.7 In-database sampling

Alongside pre-materialized transitions, the Database sub-tab carries a second per-connection performance option for very large logs: the checkbox Build sample sets inside the database. It changes how a sample set (Sample 1–3) is created — not what the sampling methods do — and, like the materialized-transitions flag, it is off by default and only exposed in the admin connection editor.

With the flag off (the default), creating a sample uses the ordinary path: the application reads the candidate journey ids for the chosen method out of the database, picks the sample in Python, and re-inserts the chosen journeys in batches. This is fine for small and mid-sized logs. On a very large log — on the order of hundreds of millions of events — extracting every journey id to the application and re-inserting in batches is slow enough to time out.

With the flag on, the whole sample is built inside Exasol: a single set-based INSERT … SELECT picks the journeys with pure SQL and writes the sample rows in one statement, with nothing extracted to the application. All three methods are supported and produce statistically equivalent results:

  • Random — a uniform sample over journeys (each journey drawn once, independent of its length).
  • Temporal — proportional across calendar-month buckets of the journey start time.
  • Path-diverse — proportional across distinct journey variants (the ordered step sequence).

The temporal and path-diverse methods use a clean proportional allocation: each bucket gets its share, and when the shares sum to more than the requested count the surplus is trimmed at random across all buckets, so no month or variant is favoured. The build runs on its own database connection with the statement timeout lifted, so a large one-shot write is not cut off mid-run.

Note This flag only affects sample creation. Existing samples, the sampling methods offered in the app, and everything downstream are unchanged. Turn it on for the connection that holds the very large log; leave it off elsewhere — small projects gain nothing and keep the simpler app-side path. Which path a given Create sample took is recorded in the admin Logging tab under operation sampling (in-database vs app-side, with the journey count and seconds), which is the quickest way to confirm the flag is taking effect.

14.8 Directory (LDAP)

The Directory tab lets the main application accept sign-ins from an LDAP directory using a search-and-bind flow. Its header states the merge model: “Directory users are created here automatically on first login as plain, enabled users — grant them a role or database connections like any other user. Local accounts always keep working.”

14.8.1 Enabling directory sign-in

Three checkboxes sit in the top banner:

Enable directory sign-in for the main app
Turns on LDAP authentication for the application itself.
Also allow directory sign-in to this admin interface
Extends it to the admin interface. Note the accompanying text: “A directory account can only reach the admin interface once it has been promoted to admin in the Users tab. Local administrators always work regardless of this setting.”

14.8.4 Configuring and testing directory sign-in

Requires: Administrator
  1. Enter the Server URI and choose the transport: LDAPS, or plain LDAP with Use StartTLS ticked. Leave Verify server certificate on and paste the issuing CA into CA certificate (PEM, optional) if it is not publicly trusted.
  2. Click Test server connection. Success reads “Server reachable — service bind OK”; a failure appears as a warning with the error text.
  3. Fill in Bind DN, Bind password, Base DN and the User filter, then adjust the three attribute names if your directory does not use uid/mail/cn.
  4. In Test a user login, enter a real Test username and Test password and click Test. Three results are stacked:
    • “Service bind: OK” or “Service bind failed: <error>”
    • “Search matched N entry/entries (<DN>)” — informational when exactly one entry matched, a warning otherwise
    • “User login: OK — <username> (<dn>)” or a warning such as “User login failed”
  5. Tick Enable directory sign-in for the main app, and Also allow directory sign-in to this admin interface only if you intend directory-based administrators.
  6. Click Save. The toast confirms “Directory settings saved”.
Tip If the user test reports more than one matching entry, tighten the User filter. A filter that can match several entries makes sign-in ambiguous, and the multi-match result is deliberately shown as a warning rather than as success.
Note Test server connection checks the server and the service bind alone; Test a user login performs the full search-and-bind for one account. Use the first to diagnose network, TLS and service-account problems, and the second to diagnose Base DN, filter and attribute problems. All saves and tests are recorded in the log under operation ldap.

Note Once a directory is configured, both sign-in pages show a small directory-server LED — a green or red dot with “Directory server available” or “Directory server unavailable”. A red dot before anyone has even typed a password usually points at the network or the service account rather than at the user.

14.9 Operational checklist

SituationWhat to do
A test or provisioning run fails with an authentication error on a connection you know worksRetype the password. Test, provision and demo generation use the typed value, never the stored one.
Users report the map is slow after an ETL loadCheck the pill in the detail pane. “⚠ Live (not built)” means TRANSITIONS_RAW is unusable — press Rebuild now, then automate it with the API token.
The map shows figures that do not match the source systemSuspect a stale TRANSITIONS_RAW. Rebuild it, or untick Use pre-materialized transitions to compare against the live query.
An LLM server is configured but always shows as unreachableLook in the Logging tab for operation llm-test. An SSRF-guard refusal is logged there but never shown to users.
A scheduler's rebuild call returns 429It is inside the 60-second per-connection cooldown. Call it once per load, not in a retry loop.
A rebuild token was lostIt cannot be recovered — only its hash is stored. Generate a new one and update the scheduler.
A directory user cannot be assigned a connectionThey have never signed in. The local record — and therefore the assignment checkbox — is created on first successful sign-in.
Everyone was disconnected unexpectedlySomeone saved the connection, changed its assignments or deleted it. This always drops live sessions immediately.
