23 Troubleshooting and FAQ

This chapter is a problem-and-remedy reference. Each entry names a symptom as you actually see it on screen, explains the cause in terms of how the application works, and gives the fix — as a numbered procedure wherever the fix is something you carry out. It covers sign-in failures, database connection failures, empty process maps, blank AI reports, imports that write nothing or write everything twice, the file watchdog, permission refusals on the integration console, licence expiry and the demo grace period, and an empty project list in the administration interface. Exact on-screen messages are quoted throughout so that you can match what you see against what is written here. Some remedies require an administrator; those carry a role callout. The chapter closes with a short list of frequently asked questions.

23.1 Before you start: where the evidence is

Three places hold nearly all the diagnostic information this application produces.

The message on screen
User-facing messages are deliberately generic where they touch security (so that an error cannot be used to discover whether an account or a connection exists) and specific everywhere else. Quote the message exactly when you report a problem.
The administration Logging tab
All three servers — the main application, the administration interface and the integration console — write into one shared structured log. Each entry carries a timestamp, severity, client IP, user, operation, an optional tag and the message. Filter by operation to isolate a subsystem (login, db-connect, db-test, db-sql, db-timeout, llm-test, materialize, import, connection, backup, tls, ldap), or by tag to follow a whole activity (SQL, DATA, BACKUP/RESTORE).
The status information in the interface itself
The connection card's status dots, the transitions pill on the process map, the checkpoint panel on a file source, and the integration console's KPI tiles each report state that no log can give you as quickly.
Tip The log records only what the configured severity allows. The default Max level logged is ERROR, which records INFO, USAGE, WARN and ERROR but not DEBUG. Raise it to DEBUG while you reproduce a database problem — that level adds the per-statement SQL trace (tag SQL, with the execution time of each statement) — and lower it again afterwards, because DEBUG is voluminous.

23.2 You cannot sign in

23.2.1 “Invalid username or password.”

Symptom. The main application or the integration console shows “Invalid username or password.” in the red error box; the password field is cleared and the username is kept. On the administration interface the equivalent message reads “Invalid credentials, or the account is not an administrator.”

Cause. The credentials are wrong — or the account is unknown, or it is disabled and the password you typed was also wrong. The message is deliberately identical in all of these cases so that it cannot be used to discover which usernames exist. On the administration interface the same message is also shown for a correct password belonging to a non-administrator, for exactly the same reason.

Fix.

  1. Retype the password. Note that a failed attempt counts towards the lockout threshold — see 23.2.2 before you try repeatedly.
  2. If you are signing in to the administration interface, confirm with an administrator that your account carries the administrator role. A perfectly valid application account gets this same message here.
  3. Directory (LDAP) accounts must exist in the directory. If the sign-in panel shows a red LED with “Directory server unavailable”, the directory itself is not answering; local accounts still work.

23.2.2 “This account has been locked after too many failed sign-in attempts.”

Symptom. The full message is “This account has been locked after too many failed sign-in attempts. Contact an administrator.” In the administration interface the account's card carries a red locked pill (tooltip “Disabled after too many failed sign-ins — Unlock to restore.”) and its action button reads Unlock.

Cause. Consecutive wrong-password attempts against a local account reached the threshold set in Users → Disable an account after N failed sign-in attempts, which is 3 on a fresh installation (0 turns the feature off). The counter is shared by all three surfaces, so wrong passwords typed at the application, the console and the administration interface all count towards the same total. A successful sign-in resets it.

Note what does not count: wrong two-factor codes, failed passkey ceremonies, directory (LDAP) accounts, and attempts against an already-disabled account. A mistyped authenticator code can therefore never disable an account.

Fix. Any one of the following.

  1. Wait. A lockout lifts itself after 15 minutes. The expiry is applied lazily, at the next sign-in attempt, so simply trying again after the window works. This interval is fixed and has no control in the interface — only the threshold is configurable.
  2. Have an administrator unlock the account. In the administration interface, Users tab, find the account and press Unlock (or Enable). This also clears the failure counter.
  3. Break glass. If the only remaining administrator is locked out, restart the servers with the environment variable PMW_RESET_LOCKOUTS=1, which clears every lockout in the installation.
Note The built-in Administrator account is counted but never auto-locked. It is the recovery account, and it must not be possible to disable it merely by knowing its name. It is protected instead by the per-IP throttle and by slow password hashing. The hint under the setting says “incl. the Administrator”; in practice the built-in account is exempt, while every other administrator account is not.

23.2.3 “This account has been disabled.”

Symptom. “This account has been disabled. Contact an administrator.” This message appears only when the password you typed was correct; with a wrong password you get the generic message instead.

Cause. An administrator has cleared the account's access, or the account was never enabled. Only enabled users may sign in.

Requires: Administrator

Fix. In the administration interface, Users tab, locate the account and press Enable. Disabling and re-enabling an account also clears its lockout counter.

23.2.4 “Too many attempts. Try again shortly.”

Symptom. HTTP 429 with “Too many attempts. Try again shortly.” on the application and the integration console, or “Too many failed attempts. Try again in about N seconds.” on the administration interface.

Cause. The per-IP throttle, which is independent of the account lockout: after 3 failures within 15 minutes from one source IP, that address waits a 5-minute cooldown measured from its last failure. It applies to password sign-ins, two-factor verification, forced enrolment, the two-factor turn-off confirmation and (in the administration interface) passkey completion. The throttle is held in memory per process and uses the socket peer address; a forwarded-for header is deliberately ignored.

Fix. Wait out the cooldown, then sign in correctly — only a fully successful sign-in clears the counter. Restarting the servers also clears it, since it is not persisted.

23.2.5 The sign-in stops and demands a QR code

Symptom. After the password is accepted the panel does not sign you in. Instead the caption changes to “Set up two-factor to continue” and a QR code appears with the text “Two-factor is required for your account. Scan this with an authenticator app (Google Authenticator, 1Password…), then enter the 6-digit code.” There is no way past it except Back, which abandons the sign-in.

Cause. This is not a fault. Allowing two-factor for an account makes it mandatory. When an administrator ticks the 2FA box for a user who has not yet enrolled, the user's next sign-in on any surface halts after the password and forces enrolment. No session is issued until a code confirms the authenticator, which is also why there are never half-enrolled accounts.

Fix.

  1. Scan the QR code with an authenticator application, or use the “Can't scan? Key” secret shown beneath it.
  2. Type the current 6-digit code into 6-digit code and press Confirm & sign in. A wrong code gives “That code didn't match. Try again.” and keeps the same QR — you do not need to rescan.
  3. The next screen shows ten one-time recovery codes. Save them now. They are displayed once, they cannot be recovered later by anybody including an administrator, and each signs you in once if you lose your authenticator. Press Copy codes, then Continue.
Warning The enrolment QR is valid for 10 minutes. If you leave it open longer you get “Setup expired. Start again.” and must restart from the username and password.

23.2.6 The authentication code is rejected

Symptom. “Incorrect code. Try again.” at the code step, or “Your sign-in session expired. Start again.” (“…Please start again.” in the administration interface).

Cause. Either the code is wrong, expired or a recovery code that has already been used; or more than 5 minutes passed between the password step and the code step, which is the lifetime of the short-lived “password ok” state. Codes are 6 digits on 30-second steps with one step of clock-skew tolerance either way, so a device whose clock has drifted by more than about a minute will fail every time.

Fix.

  1. Wait for a fresh code and retype it. Spaces are ignored.
  2. Check the clock on the device running the authenticator; enable automatic time synchronisation.
  3. If you no longer have the authenticator, type one of your recovery codes in the same field. Dashes, spaces and case are ignored. Each code works once.
  4. If both are lost, an administrator must untick 2FA for your account in the Users tab. Your password alone then signs you in and you can enrol again. There is no administrator function that resets two-factor while preserving the enrolment, because the secret cannot be read back.
Note Unticking 2FA relaxes the requirement but does not delete the stored secret. Re-ticking it re-arms the same authenticator with no new enrolment. Only turning two-factor off from the 🔒 Two-factor sheet (which requires a current code) deletes the secret and the recovery codes.

23.2.7 Right credentials, wrong surface

Symptom. Your username and password work in one place and are refused in another.

Cause. The three surfaces admit different people, and their session cookies are audience-bound: signing in to one does not sign you in to the others.

Note that the console's role check runs before any second factor, so a refused power user never even reaches the code step.

Note The integration console always requires a sign-in, even when the main application is running in open mode with “Require sign-in for the main application” switched off. The administration interface does too.

23.2.8 “Console unavailable”

Symptom. The integration console answers a browser navigation with a 503 page titled Console unavailable: “The integration console has been turned off by the administrator.” Programmatic calls get the same text as JSON.

Cause. The checkbox Enable the integration console in the administration interface's Integration tab is cleared.

Requires: Administrator

Fix. Tick Enable the integration console (toast “Integration console enabled — restart to apply”), then press ↻ Restart app server in the App Control tab. The change is stored immediately but only takes effect on restart.

23.2.9 The passkey button is missing, or a passkey sign-in fails

Symptom. The 🔑 Sign with Passkey button does not appear; or it appears and produces “Passkey sign-in failed.” (“…Check the passkey is registered and still enabled.” in the administration interface); or enrolment reports “Passkeys need a hostname, not an IP address.”

Cause. One of four:

  • The browser does not support WebAuthn (“This browser does not support passkeys.”).
  • The page was reached by a bare IP address or a single-label host. WebAuthn binds a passkey to a domain name and rejects both, so the controls hide themselves. Off localhost, a secure context (HTTPS) is required as well.
  • An administrator has not allowed passkeys for the account, or has revoked the permission — which blocks passkey sign-in immediately, existing passkeys included.
  • You did not type a username. The flow is username-first: type the name, then press the button.

Fix.

  1. Reach the server by a resolvable name over HTTPS — its .local Bonjour name or a DNS entry — and issue the TLS certificate for that name. Password sign-in works over an IP either way.
  2. Ask an administrator to tick Passkey for your account in the Users tab, then enrol from 🔑 Passkeys next to Sign out while signed in with your password.
  3. For a deployment that splits the application and the administration interface across sub-domains, set PMW_PASSKEY_RP_ID to the shared parent domain and list the expected origins in PMW_PASSKEY_ORIGINS.
  4. If enrolment reports “A passkey for this account already exists on this device.”, remove it from the device's own passkey settings (on iOS: Settings → Passwords) and try again.

23.2.10 You are signed out unexpectedly

Symptom. The application returns to the sign-in panel, sometimes with the orange notice “You were signed out due to inactivity.”; or requests start failing with 401 “Authentication required.”

Cause. One of the session rules below.

Fix. Sign in again. If it happens constantly, ask an administrator to review the idle timeout. If you lose the integration console specifically and see the Access denied screen (“The integration console is available to developers and administrators only…”), your Developer role was revoked mid-session.

Note The integration console has no client-side idle watcher. Its session expires server-side after the same idle window as the application, but nothing bounces you to the sign-in screen — you discover it when your next action fails.

23.3 Database connection failures

When you tap a connection card, the first status dot turns orange and an error is reported. The messages a normal user sees are deliberately generic: no Exasol codes, internal hostnames or SQL-state fragments reach the browser. The full driver detail is written to the log under operation db-connect. Power users and administrators running Test see the same categories with the raw driver detail appended.

23.3.1 The message catalogue

MessageCauseFix
“Authentication failed — check your username and password.” The database rejected the credentials stored on the connection. The connection's database user and password are managed by an administrator (or by the power user who created it). Ask them to correct and re-test it. You never type a database password into the application.
“Connection timed out. Verify the host address, port, and network connectivity.” The socket did not open within the fixed 15-second connect timeout — usually a firewall silently dropping packets, or an unreachable network. Check routing and firewall rules between the server and the database host and port (8563 by default).
“Connection refused. No server is accepting connections at this host and port.” The host answered but nothing is listening on that port. Verify the port number and that the database is running.
“Host not found. Check the hostname spelling and your DNS / network connectivity.” Name resolution failed. Correct the hostname, or use an address that resolves from the application server.
“TLS certificate error. Try 'Skip verification' or configure a fingerprint in the server's security settings.” The connection uses TLS in Verify (system trust store) mode and the server's certificate is not trusted, has expired, or does not match the hostname. See 23.3.2.
“This connection is set to pin a certificate fingerprint, but the fingerprint is missing or not hexadecimal. Enter the server's SHA-256 fingerprint, or change the certificate mode.” Certificate mode is Pin fingerprint but the fingerprint field is empty or contains something that is not hexadecimal. See 23.3.3.
“The database rejected the request.” An Exasol query error — most often a missing schema, a missing table, or no SELECT privilege. Check the schema name on the connection and the account's privileges (see 23.3.4). The detail is in the log.
“Connection failed. Check the host, port, and credentials.” Fallback for anything not classified above. Read the log entry under operation db-connect.
“This connection changed during sign-in. Please reconnect.” An administrator edited or deleted the connection while your (slow) connect was still in flight, so the freshly opened session was dropped. Refresh the Connections list with ↻ and connect again.
“This connection is not available to you.” (403) / “Connection not found.” (404) The connection is no longer assigned to you, or no longer exists. Refresh the list; ask an administrator to reassign it.
“Not connected to a database.” (409) A data request arrived with no live session — typically after a forced disconnect. Tap the connection card again.

23.3.2 TLS certificate errors

Cause. Certificate mode is Verify (system trust store), the default, and the database's certificate cannot be validated against the trust store — a self-signed certificate, a private CA the server does not know, an expired certificate, or a hostname mismatch.

Requires: Power user (own connections) or Administrator

Fix. Open the connection editor and choose the mode that matches your situation.

  1. Verify (system trust store) — correct for a certificate issued by a CA the server trusts. If that is what you intend, install the CA certificate in the server's trust store rather than weakening the connection.
  2. Pin fingerprint — correct for a self-signed or private-CA certificate whose identity you can confirm out of band. Paste the server's SHA-256 fingerprint into Fingerprint (SHA-256). Colons are stripped; the value must be pure hexadecimal, 16 to 128 characters.
  3. Accept any (insecure) — disables certificate and hostname verification. Acceptable only in a laboratory.
  4. Press Test connection, then Save.
Warning Mode parsing fails closed: any stored value that is not recognised — a typo, or legacy data from a restored backup — is treated as Verify, never as no verification. A connection that used to work after a restore and now reports a certificate error has most likely landed in this state.
Note The field Minimum RSA key size (default 2048) is stored and carried through every operation for compatibility with the macOS application's connection records, but the web backend does not currently enforce it. Do not rely on it to solve a handshake problem.

23.3.3 Fingerprint missing or mismatched

Symptom. The connection refuses to open with the “set to pin a certificate fingerprint” message, or — where the fingerprint is well-formed but wrong — with the generic TLS certificate error.

Cause. In Pin fingerprint mode the driver pins the server's certificate to the value you supplied. A blank or non-hexadecimal value is refused outright rather than silently falling back to no verification, which is why the message is so specific. A well-formed but incorrect fingerprint means the certificate on the server is not the one you pinned — either it was legitimately replaced, or you are not talking to the server you think you are.

Fix. Obtain the current SHA-256 fingerprint from the database administrator, paste it into the field and test. If the certificate was rotated, update the pin. If it was not rotated, do not update the pin — investigate.

23.3.4 Connected, but features fail

Symptom. The connection opens, but a specific feature reports an error while the rest of the application works.

Cause. The database account lacks a privilege that only that feature needs.

FeatureRequired database privilege
Every read feature (maps, charts, KPIs)SELECT on PROJECTS, JOURNEYS, STEPS, METAS
Notes (first use creates the table)CREATE TABLE, then INSERT and DELETE on NOTES
Journey sampling (adds the SAMPLE_SET column)ALTER TABLE and INSERT on JOURNEYS

Create schema & tables, demo contentCREATE SCHEMA, CREATE TABLE and (for demo data) INSERT

Fix. Ask the database administrator to grant the missing right. The application cannot grant database privileges to itself.

23.3.5 “Test connection” fails although the saved connection works

Symptom. A connection that users connect to happily reports an authentication failure the moment you press Test connection, Create schema & tables or Generate in the editor.

Cause. These three operations use the password as typed in the form, never the stored one. On a saved connection the password field is blank (it shows “•••••• (unchanged)” or the hint “(set — leave blank to keep)”), so the test runs with an empty password.

Fix. Retype the password into the field before testing or provisioning. Leave it blank again — or simply press Cancel — if you do not want to change the stored secret; a blank field on save keeps the stored value unchanged.

23.3.6 The Connections list is empty

Symptom. The sidebar Connections section lists nothing.

Cause. No connection has been assigned to your account. Each user sees only their assigned connections.

Fix. Press ↻ in the Connections header first — the list does not refresh itself after an administrator grants access. If it is still empty, ask an administrator to assign one in Database Connections. If you hold the power role, create your own with the ＋ button; every connection you create is assigned to you automatically.

Note Saving any change to a connection, changing its assignments, or deleting it immediately disconnects every user currently using it. That is intentional — a revoked assignment must take effect at once — but it means a connection can drop out from under you while you work.

23.3.7 “Unable to load data” after the page has been idle

Symptom. After the browser has been left open and idle for a while — or after an automatic idle sign-out and a fresh sign-in — the first action (a refresh, opening a project, loading a chart) fails with “Unable to load data”, and in older builds you had to reconnect the connection and reselect the project before anything worked again.

Cause. The backend keeps one long-lived database session per connection. A network device between the server and the database — very commonly the host.docker.internal NAT when the database is reached from inside a container — silently drops a socket that has sat idle, while the backend still believes the session is open. The next statement then meets a dead socket and the driver raises “Exasol connection was closed”.

Fix. None is needed on current builds. The backend now detects a dropped-socket error, transparently reopens the connection and retries the statement once, so the action simply succeeds. A genuine query error (bad SQL, a missing object) is not retried — it surfaces immediately as before. Only if the reopen itself fails (the database is genuinely down or the credentials no longer work) will you see a connection error, and then the remedies in 23.3.1 apply. If you are on an older build and still see this, reconnect the connection once; upgrading removes the need.

23.4 The process map is empty or wrong

23.4.1 No nodes appear

Symptom. A project is selected but the map area stays empty, or Filtered Journeys reads 0 while Total Journeys is greater than 0.

Cause and fix, in the order worth checking:

  1. The date window excludes your data. When a project is first selected, A-Chart loads the last 30 days before the latest event (Configuration → Default date window; 0 loads the full range). Widen the slider, or set the default to 0 and reload the project — the setting takes effect on the next project load and does not move the slider on the current map.
  2. The filters exclude everything. Every filter works at journey level: a journey qualifies in full or not at all. An Exclude Steps entry, a narrow Num Steps, Journey Time or Journey Score range, or a meta value with a typo will empty the map. Press Reset, then Apply.
  3. You did not press Apply. Filters are never applied automatically. In A/B Comparison, Apply reloads only the active side — the one marked with the pencil icon and the “editing” label.
  4. You are looking at B-Chart. B-Chart starts empty by design. Apply filters, or press Load on its empty state.
  5. The selected sample set is empty. If the A or B slot in the Sampling section points at a sample that was deleted, or at a stored simulation result that was never produced, there is nothing to draw. Switch the slot back to Original data.

23.4.2 The map shows “⚠ Live (not built)”

Symptom. The pill in the chart header reads ⚠ Live (not built) instead of ⚡ Pre-materialized, and interactive filtering is slower than expected.

Cause. The connection has Use pre-materialized transitions switched on, but the TRANSITIONS_RAW table is missing, has never been built, or could not be read. This is a fail-safe, not a fault: the map falls back to the live windowed query so it never breaks. The exact cause is logged under operation materialize.

Requires: Administrator

Fix.

  1. Open Database Connections, edit the connection, and press Rebuild now in the Use pre-materialized transitions banner. The status line then reads “Last built: <date> · N pairs.”
  2. If the rebuild fails, read the red status text and the materialize entries in the log.
  3. Schedule a rebuild as the last step of every load of JOURNEYS. The table is a snapshot and goes stale the moment the event log changes; generating demo data and creating or deleting samples do not rebuild it either. Use the per-connection bearer token and POST /api/connections/<id>/rebuild-transitions on the administration server for that.
Note Two rebuilds of one connection never overlap — the second gets 409 “A rebuild is already running for this connection.” Token-triggered rebuilds also carry a 60-second per-connection cooldown (429 “Rebuild throttled — try again in Ns.”); an administrator pressing Rebuild now is never throttled.

23.4.3 A KPI tile shows “—”, or Statistics reports a timeout

Symptom. The Process Goodness tile shows a dash, or the Statistics view reports “Statistics query timed out (30 s). Narrow your date range or filters and try again.”

Cause. Heavy statistics queries (variants and routes, and the goodness metric) carry a 30-second timeout, configurable with PMW_QUERY_TIMEOUT. The goodness query groups journeys by path pattern, which is expensive on a large, heavily filtered dataset. Timeouts are logged under operation db-timeout. A dash can also simply mean that no step has a SCORE — with no scores configured in STEPS the tile is hidden altogether rather than dashed.

Fix. Narrow the date range or add filters and reload. For a lasting improvement, index JOURNEYS (PROJECT_ID, EVENT_TIME) and JOURNEYS (PROJECT_ID, EVENT_ID), and consider enabling pre-materialized transitions on the connection.

23.5 AI supported Documentation stays blank

Symptom. The AI supported Documentation view produces no report, or produces only the locally computed sections.

Cause. The view sends the current A-Chart transition table and your prompt template to an OpenAI-compatible endpoint configured on the active connection. Without a reachable model server there is nothing to render. The journey-paths table, happy-path conformance, the conformance gap analysis and your notes are computed locally and never sent to the model — which is why those sections can appear while the model's answer does not.

Fix.

  1. Look at the connection card. A second status dot appears only when an LLM server is attached, and it must be blue. Orange means the model server did not answer; no second dot at all means no LLM is configured on this connection.
  2. Ask an administrator (or the power user who owns the connection) to fill in Server URL, Model and, if required, API key on the connection's LLM tab, and to press Test connection. A successful probe reports “LLM: reachable — N models”; a failure reports “LLM server not reachable.”
  3. The probe is a GET <serverURL>/models with a 5-second timeout. A server that is merely slow to start will read as unreachable; retry once it is up.
  4. If the URL looks correct and the probe still fails, check the log under operation llm-test. The outbound SSRF guard refuses some URLs outright and records why — for example “Only http:// and https:// URLs are allowed.” or a refusal because the host resolves to a link-local or cloud-metadata address. Such a refusal is never shown to end users; the model simply reads as unreachable. Loopback and private addresses are allowed by default so that local model servers work, unless the deployment sets PMW_BLOCK_PRIVATE_LLM_HOSTS=1.
Warning AI models can produce results that are incorrect, incomplete or misleading. Verify every finding independently before acting on it.

23.6 Import problems (integration console)

23.6.1 The import wrote zero rows

Symptom. A run finishes without error but nothing new appears in the project.

Cause. There are two entirely different reasons, and the run result distinguishes them. This is why the result reports linesRead separately from records.

What the run reportsWhat happenedFix
“Nothing new to import — the file has not grown since the last import.” A delta run found no bytes appended past the checkpoint. Normal, not an error. Nothing to do. Append to the file, or switch delta upload off to read from the top again.
“Nothing to import — the file is empty.” The file has no content at all. Check the path. Remember relative paths resolve inside the server's integration files directory.
Lines were read but 0 events written and a high Events skipped count A real misconfiguration: the source type's regular expressions do not match this log. A line becomes an event only if the case id, the step and the timestamp are all captured and the timestamp normalises. See below.

Fix for the third case.

  1. Open the linked source type and paste a genuine line from the log as the sample. Each field row shows live what it captured; a wrong pattern is immediately visible.
  2. Check that a field with the role EVENT_TIME exists — without one the run is refused with “The source type has no timestamp field.”
  3. Check the Example JOURNEYS record panel. It shows exactly the row the specification would produce, marks the id as “stored as MD5” and marks a compound-derived step with “compound”.
  4. Give each field's regular expression exactly one capturing group — that group is the value. Without a group the whole match is used.
  5. Remember that every line is truncated to its first 2000 characters before matching. A pattern aimed at content beyond that will never match.
  6. Verify the timestamp interpretation. Numeric dates default to day-first (European); a 12-hour AM/PM clock flips the interpretation to month-first. Yearless syslog timestamps are given the current UTC year, which mis-years an old log imported around the turn of the year.
Tip A non-zero Events skipped KPI is highlighted in orange for exactly this reason. It exists so that a silently misconfigured source type shows up as “lots skipped” rather than merely as a small event count.

23.6.2 Only part of a large file was imported

Symptom. A first import of a large existing file stops well short of the end; running it again imports more.

Cause. One read — a manual run or a watchdog poll — consumes at most 8 MB of new bytes. A larger backlog is drained across successive reads, cap by cap. A single “line” longer than the whole 8 MB cap is treated as unparseable content and skipped past rather than re-read for ever.

Fix. Press ▷ again (or let the watchdog poll again) until the checkpoint reaches the end of the file. The checkpoint panel shows how far into the file the reader has got.

23.6.3 Duplicate events after re-importing

Symptom. After importing the same file twice the project holds every event twice; journey counts and transition counts are inflated.

Cause. Events are never de-duplicated. The importer appends one JOURNEYS row per parsed event; it does not check whether an identical row already exists. Three routes lead here:

  • Switching delta upload off, which re-reads the file from the top.
  • Pressing ↺ Reset checkpoint, which forgets the read position but deletes nothing from the database.
  • Retrying after a run that failed part-way. On failure the currently open transaction bracket is rolled back, but brackets already committed stay committed — while the checkpoint does not advance for a failed run. The retry therefore re-reads lines whose rows are already in the database.

Fix.

  1. To reload a project genuinely: delete the project first, in the connection editor's Projects tab, then import again. Deletion clears the project's rows from PROJECTS, JOURNEYS, STEPS, METAS, NOTES and TRANSITIONS_RAW and cannot be undone — notes attached to the project go with it.
  2. To make a failed run leave nothing behind, set the source's Transaction bracket to 0, which commits the whole import as a single transaction: all of it lands, or none of it. The default is 5000 rows; any other value is clamped to the range 1000 to 1,000,000, and a non-numeric value falls back to 5000.
  3. Leave delta upload on for routine top-ups. Running the same source twice then adds only what was appended since the last run.
Warning There is one checkpoint per source, shared by manual runs and the watchdog. Resetting it also makes the watchdog re-read the file from the start. Changing a source's file path deletes the checkpoint automatically, so the next import — manual or watchdog — reads the new file from the beginning.
Note Changed compound-step rules apply only to future imports. Rows already written keep the step names they were given. To re-apply changed rules to existing data, delete the project and import again.

23.6.4 The watchdog is not importing

Symptom. A file source is marked with 👁 but its checkpoint never advances, or the console reports no watchdog imports.

Cause and fix. Work down this list; the failure reason is recorded on the source's checkpoint as lastError and also written to the log (tag DATA, operation import) as “watchdog import failed: '<source>' — <message>”.

23.6.5 Permission denied on the integration endpoints

Symptom. An integration request fails with HTTP 403 and one of two messages: “You need the Developer role to use the integration features.” or “The integration console is turned off.”

Cause. Every integration endpoint sits behind one router-level gate on the shared compute backend, so it protects the API no matter which surface proxies the call. In order, the gate checks: whether the deployment runs without sign-in at all (in which case the surface is open); whether the administrator has switched the integration surface off; and finally whether the signed-in user exists, is enabled, and holds the Developer or administrator role. Power users are deliberately refused — the check exists precisely so that the main application's proxy cannot be used to bypass the console's own role gate.

Requires: Administrator

Fix.

  1. For “You need the Developer role…”: in the administration interface, Users tab, press Make developer on the account (logged as “granted the Developer role for '<user>'”). The role is re-checked on every request, so a grant takes effect immediately — and a revocation drops the user to the Access denied screen mid-session.
  2. For “The integration console is turned off.”: tick Enable the integration console in the Integration tab and restart from App Control.

23.7 Licence expiry and demo mode

23.7.1 The application stops responding after a while

Symptom. The sign-in panel carries the orange banner “Demo Mode — remaining time: N min”, then “No License installed”. Eventually the application's API calls fail with 502 “The compute backend is not reachable. Start it with ./run.sh or check PMW_BACKEND_URL.” The administration interface keeps working normally.

Cause. The application requires a valid licence. Without one it runs for a one-time grace period — 30 minutes by default, set with PMW_LICENSE_GRACE_SECS — after which the compute backend stops. The grace window is granted once per installation and stamped in a marker file; restarting does not renew it, and deleting a licence cannot reset it. The administration interface is deliberately left running so that a licence can always be applied.

Requires: Administrator

Fix.

  1. Open the administration interface (it is still reachable) and go to App Control → License.
  2. Choose the issued license.json file and press Upload license. The signature is verified before anything is stored; a forged or corrupt file is rejected with the specific reason and nothing is written.
  3. On success the panel reports “License installed. The backend applies it within a few seconds.” No restart is needed — the backend polls for it. Uploading a valid licence during the grace period cancels the pending shutdown.
  4. Confirm the green status banner: “Licensed to '<name>', valid until <date>.”

23.7.2 The licence status banner is red or orange

BannerMeaning and remedy
Orange: “License for '<name>' expired on <date>.”The licence is genuine but out of date. Obtain a renewal and upload it.
“No license installed.”Nothing has been uploaded, or the licence was deleted. Upload one.
“License signature is not valid.” / “License signature is malformed.”The file was altered or is not the one you were issued. Request a fresh file; do not edit a licence by hand.
“License file is not valid JSON.” / “License file is missing 'license' or 'signature'.”The wrong file was uploaded, or it was truncated in transit.
“License has no valid expiry date.” / “License file could not be read: …”Contact your supplier with the exact text.
413 “License file is too large.” / “Invalid file content.”The upload exceeded the size cap or was not decodable. Check that you selected the right file.
Note 502 “The compute backend is not reachable…” and 504 “The compute backend timed out.” are proxy errors, not licensing errors as such. They mean the compute backend is down or overloaded — which an expired grace period causes, but so does a backend that was never started.

23.8.2 The administration page stops responding after a restart

Symptom. You pressed ↻ Restart app server and the administration page no longer loads.

Cause. One restart rebinds all three servers — the main application, the integration console and the administration interface — because they share the TLS mode and the active certificate. If you changed the TLS mode, the administration interface itself moves between http://…:8090 and https://…:8453.

Fix. Reconnect on the other address. If the restart fails outright, the exact messages are: 409 “The app server is not managed by the launcher (no PID file). Start it with ./run.sh, then try again.”, 409 “The app server process is not running.”, 500 “Invalid PID file.” or 500 “Could not signal the app server: <os error>”.

Note If a mode requires HTTPS but no certificate is active, every server falls back to HTTP on restart so that nothing — including the administration interface — becomes unreachable. The TLS tab warns about this in advance: “No active certificate — HTTPS cannot start. Generate or upload one and activate it below.”

23.9 Frequently asked questions

Why can I not see the Conformance Check, Happy Path and Simulation views?
They are shown only to power users and administrators. They are also hidden — for everybody — when the installation runs in open mode with sign-in switched off, because there is then no identity to hold a role. Their APIs answer 403 in that state. There is no way to have both no-login access and the power features at once.
Why can I not see the Sampling section?
Same reason. Sampling rewrites the shared sample sets for everyone on the connection, so it is a power-user capability rather than a personal one.
Why does the map look different for a colleague using the same project?
Filters, presets, node layouts, KPI arrangement and personal settings are per user. Notes, sample sets and everything in the STEPS table are shared, because they live in the database.
Why can I not edit a connection that appears in my sidebar?
The ✎ button appears only on connections you created. A connection an administrator created and assigned to you can be used but not edited.
I typed a friendly reference into the Event ID field and got nothing.
Anything that is not already a 32-character hash is MD5-hashed before the query. In the demo datasets the stored EVENT_ID is the MD5 hash of a synthetic reference such as ORD-000001, so typing that reference works. Imported data behaves the same way: the integration console always stores EVENT_ID as the MD5 of the captured id, so the raw identifier cannot be recovered from the database.
Why did my filter preset not update after I changed the filters?
A preset is a snapshot taken at the moment you saved it. Later filter changes do not update it. Save a new preset, or rename and re-save.
Why is the Process Similarity badge missing in A/B Comparison?
The variant set is capped at 500 per side (1000 combined). Beyond the cap the badge is hidden rather than showing a misleading score from a biased sample. Narrow the filters on either side.
Where do rotated log files and scheduled backups go?
Rotated logs to data/logs/ (only the newest ten archives are kept; Clear empties the live log only). Scheduled backups to data/backups/, named by timestamp and pruned to the retention count.
Why did no scheduled backup run last night?
The scheduler runs inside the administration server process — nothing is written while that server is down. A tick with no stored password records the failure “No backup password is set.” The cron expression is matched against the wall clock of the display timezone set in App Control → Timezone.
Can an administrator recover my recovery codes or my two-factor secret?
No. The secret is stored encrypted and the recovery codes only as hashes. The recovery path is for an administrator to untick 2FA for your account so that your password alone signs you in and you can enrol again.
